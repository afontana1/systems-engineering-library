Why this idea matters

A systems engineer must produce a decision that remains defensible when the conditions change. This chapter focuses on model-based analytics and decision queries: how to reason from purpose and evidence to a bounded action. The objective is not to memorize a term, but to state what it permits, when it fails, and what observable evidence would change your conclusion.

Build the mental model

Link an engineering question to a reproducible computational chain: required source fields, units, constraints, transformations, scenario versions and output assertions. Queries should be designed before building dashboards. A decision record needs both the result and an explanation of how it changes under plausible assumptions. Link evidence identifiers to exact model configurations.

Useful diagnostic distinction: A parametric result without parameter provenance cannot be reviewed or reproduced.

The underlying mechanisms: lessons to retain

The following instructional notes are adapted from the corresponding original course guide. They form a compact mechanism checklist to use while reading the new explanation and doing the chapter exercise.

  • Analytics include structural queries, coverage matrices, graph paths, calculations, simulations, sensitivity, and generated reports.
  • Queries should have controlled definitions, test cases, expected results, failure behavior, and version compatibility.
  • Change impact is a graph/reasoning problem: a change propagates through semantics, allocations, interfaces, analyses, evidence, decisions, and products.
  • Automated reports are only trustworthy when source authority, transformation logic, query version, and configuration are recorded.
  • Case studies should be analyzed for actual decision improvement, not retold as success stories.

Worked reasoning: the Northstar mobility case

Compare two charging designs with energy demand, bus utilization and charger uptime. A computed throughput score depends heavily on winter battery derating; preserve that scenario and explain why a single mean-value score would mislead.

Compare with the guide's worked case

The original guide uses the following short case discussion. Reproduce the reasoning with a changed assumption rather than copying its conclusion.

A query reports 100% requirement verification coverage, but the example discovers that 12 verification cases point to superseded identifiers and two tests use an old interface version. The worked analysis distinguishes syntactic link coverage from valid evidence coverage and generates a corrected decision dashboard with uncertainty and stale-data warnings.

Reproduce the example using controlled course data, change one assumption, and explain how the decision or evidence changes.

How to challenge the example

  1. Boundary: Name the engineered product, process, actors and environment relevant to this claim. List one important exclusion.
  2. Evidence: Identify one source that would let an independent reviewer reproduce or falsify the result.
  3. Failure mode: Test what happens when an input is stale, unavailable, biased, incorrectly configured or in conflict with another artifact.
  4. Decision: State who can authorize the next action, which guardrail could block it, and how the decision will be recorded.

Learning objectives from the original guide

  • Design and execute model queries, matrices, calculations, and generated reports.
  • Connect descriptive model elements to analytic models, data, uncertainty, and decision criteria.
  • Perform change-impact analysis across mission, requirements, architecture, interfaces, simulations, tests, and decisions.
  • Evaluate a real-world or public case using the course decision/evidence framework.
  • Conduct and respond to the Model, M&S, and MBSE Analytics Review.

Practice questions with guided answers

Attempt the questions before expanding each answer. These five knowledge checks and their answer guidance are adapted from the supplied Week 6 course guide; their inclusion does not replace the larger independent assignment.

  1. Why can 100% trace coverage still be misleading?

    </details>

  2. What should a query specification contain?

    <details><summary>Show explanation</summary>

    Question, semantic logic, inputs, scope, expected result, test data, version, and failure behavior.

    </details>

  3. What is model-based change impact?

    <details><summary>Show explanation</summary>

    Identification of affected model elements, analyses, interfaces, evidence, products, owners, and decisions due to a controlled change.

    </details>

  4. Why test generated reports?

    <details><summary>Show explanation</summary>

    Transformation and query defects can produce polished but wrong decision products.

    </details>

  5. What makes a digital-engineering case credible?

    <details><summary>Show explanation</summary>

    Clear baseline, decision, intervention, evidence, result, limitations, and plausible causal mechanism.

    </details>

Extended transfer exercise

Construct a one-page claim–evidence–decision map for this week's topic. Include a claim, current baseline, configuration or version, measurable response, source and timestamp of evidence, alternative explanation, reviewer, unresolved uncertainty and stop/go rule. Then deliberately inject one defect (missing source, wrong version, unexpected consequence or inadequate coverage) and explain how the decision should change.

Stretch: Use a second scenario with a different consequence level or stakeholder group. Explain why the same method may require different assurance controls.

Bridge to the assessed curriculum

The companion explains the concepts; the original guide supplies the complete assignment, sources, rubric and formal mastery gate. This is the guide's weekly deliverable:

Model Analytics and Midcourse Review Package containing query catalog, executable source, test cases, generated matrices/reports, linked analytic model, change-impact analysis, case-study review, live demonstration, findings, and corrections.

Submit native or textual source, data and transformations, generated views, query/analysis source, a change log, and a one-page self-review. Screenshots alone are not acceptable evidence.

Common critical failures to avoid (from the guide):

  • Counting links as valid evidence without checking status, identity, version, and acceptance.
  • Using screenshots without executable query or transformation source.
  • Failing to detect the controlled identifier inconsistency.
  • Claiming benefit from a case without identifying the decision and evidence.

Mastery and revision standard:

Pass the live review with all required queries reproducible, the injected inconsistency detected and corrected, generated products tied to controlled source, and no critical stale-evidence or change-impact gap.
