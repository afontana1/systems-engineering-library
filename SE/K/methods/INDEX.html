Engineering method guides

These guides give a full technical explanation of methods needed in the curriculum: the underlying model, assumptions, a worked engineering calculation or executable state model, interpretation, limitations, and a path to the course and textbook material. They supplement the canonical concept articles and course-aligned textbooks without displacing them.

Foundations: first set

  1. Requirements engineering and verification evidence — requirement formulation, timing budgets, test design, statistical acceptance, and evidence sufficiency.
  2. Bayesian decisions and value of information — posterior actions, EVPI/EVSI, sensitivity, and uncertainty.
  3. MBSE semantics and executable checks — typed graph semantics, parametric feasibility, and evidence configuration.

Expanded methods: second set

  1. Statistical inference and design of experiments — estimands, confidence intervals, factorial effects, interactions, and reproducible experiment analysis.
  2. Reliability analysis with censored failure evidence — hazard, exponential lifetime MLE, Kaplan–Meier, dependence, and repair-versus-survival interpretation.
  3. Pareto search, scenario regret, and robust design — dominance, constraints, scenario probabilities, regret, robust feasibility, and engineering preference models.
  4. MBSE behavioral contracts and bounded checking — transition relations, state invariants, idempotence, counterexample traces, and finite-model limitations.

Simulation, uncertainty, and software contracts: third set

  1. Simulation output analysis and model credibility — warm-up, independent replications, paired common random numbers, uncertainty intervals, verification versus validation, and NASA-style intended-use statements.
  2. Uncertainty propagation with dependent inputs — covariance propagation, delta method, correlated Gaussian inputs, Monte Carlo tail estimates, and input-model limitations.
  3. UML and OCL software contracts — class-model invariants, preconditions and postconditions, snapshot counterexamples, and persistence/concurrency enforcement boundaries.

Safety, evidence, and one connected engineering case: fourth set

  1. Safety engineering, fault trees and assurance — hazard/control distinction, minimal cut sets, common-cause dependencies, numeric sensitivity, and claim–evidence review.
  2. MBSE baselines and evidence currency — typed graph constraints, stale evidence, change-impact queries, and precise limits on JSON versus actual SysML v2 validation.
  3. Campus Mobility: integrated engineering case — one synthetic case through needs, requirements, interfaces, architecture, hazard analysis, alternatives, acceptance evidence and release decision.

Language validation, advanced simulation, transactional correctness and case artifacts: fifth set

  1. SysML v2 modeling and traceability — typed definitions and usages, trace semantics, explicit OMG pilot-parser validation procedure, and cross-document audit; the included illustration is not claimed as parser-validated SysML.
  2. Simulation calibration and rare-event analysis — Poisson likelihood and profile interval, withheld count challenge, normal-tail importance sampling and the distinction between numerical precision and physical credibility.
  3. Transactional concurrency and assurance — a reproducible check-then-act race, partial unique index, retries, local invariants and distributed boundaries.
  4. Campus Mobility controlled artifact package — editable requirement set, interface control extract, VCRM, hazard/assurance register, baseline change-impact record and auditable cross-document identities.

Each guide has an editable Markdown source and a corresponding .html reader; the site uses its local MathJax, with no online math service. The reproducible programs use the Python standard library; Phases 4–5 add fault-tree, baseline-audit, document-crosswalk, calibration and transactional-concurrency programs with a controlled and a deliberately stale JSON fixture. All values are synthetic teaching examples and are not field measurements or guarantees.

How to study a method

Start with the problem and assumptions, work the example by hand, reproduce the executable results, change one assumption and predict how the conclusion will change, then return to the course assessment. A project decision still requires validation of the relevant data, operating context, and decision authority. These guides are reference instruction, not automatic verification or certification.
