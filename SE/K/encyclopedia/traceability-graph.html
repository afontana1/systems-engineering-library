Requirements traceability: a typed graph of engineering claims

Reference entry · MBSE and configuration management · Expanded reference

What traceability means

Traceability is the ability to follow justified relationships among stakeholder needs, requirements, functions, architecture elements, interfaces, hazards, implementation artifacts, tests, results, and decisions. It is not a spreadsheet of arbitrary hyperlinks. A good trace says what relationship is asserted, why it is valid, who authorized it, and which versions it connects.

Different edges mean different things. A lower-level requirement derives from a system requirement; a function satisfies an outcome; a test verifies a requirement; a design choice addresses a hazard; a file implements an element. These verbs cannot be interchanged without losing reasoning.

Graph semantics and impact

Let G = (V, E, τ) be a directed graph whose vertices are versioned artifacts and whose edges carry typed relationships τ. Traceability questions become graph queries: Which requirements lack verifying evidence? Which hazards depend on an obsolete component version? Which tests must be reconsidered after an interface schema changes? Reachability provides candidate impact, but semantic edge direction matters; not every connected artifact is actually invalidated by a change.

A simple traceability coverage metric is C = |R_with_valid_evidence| / |R_applicable|. It is only meaningful after specifying which requirements are applicable, how evidence is judged valid, and whether evidence is current. A 100% populated matrix may still be wrong if all links were generated by keyword matching or if an entire important stakeholder need was never translated into a requirement.

Worked impact-analysis example

A shuttle service changes the identifier format used in booking requests. The interface contract is revised from v3 to v4. The trace graph links that contract to dispatcher parsing code, integration tests, audit logging, duplicate-request handling, and the requirement prohibiting duplicate bookings. Even if the developer changes only one schema file, the affected claims extend into timing, interoperability, privacy, and operations.

Suppose 20 tests are linked to the interface, but only 12 were executed on the new build. Reporting 20/20 covered counts link presence rather than current evidence. A defensible report distinguishes 20 mapped, 12 re-executed, 8 pending impact review, and any tests whose relevance changed. Version identity prevents old green results from being mistaken for proof about new software.

A credible traceability workflow

  1. Define controlled artifact types and allowed relationship semantics.
  2. Give artifacts stable identifiers and version or baseline provenance.
  3. Record the rationale for critical edges, not just their endpoints.
  4. Enforce graph checks for orphan requirements, unverified obligations, conflicting allocation, and stale evidence.
  5. Trigger impact analysis from a changed baseline and review transitive dependencies.
  6. Apply human engineering judgment to determine whether a reachable claim actually requires rework.
  7. Preserve review decisions and the new graph state under configuration control.

Weak points and false assurance

Automated link suggestions are useful triage, not proof of a relationship. Dense graphs can conceal an absence of meaningful evidence. A verification test attached to the wrong configuration is not current proof. Reverse traceability must expose unjustified features as well as unmet needs; otherwise expensive functionality can accumulate without a mission rationale.

Connections

Traceability ties together requirements, architecture allocations, safety arguments, test plans, change control, digital-thread semantics, software release identity, and enterprise governance. It provides navigable evidence, not automatic truth.

Technical analysis: traceability is a versioned evidence graph

Traceability should be represented as a directed, typed graph: need → requirement → function → architecture element → verification case → result. Each edge has meaning and validity conditions. A link from a test to a requirement does not prove coverage if the test's operating mode is wrong, the requirement revision changed, or a shared failure mechanism is absent from the test.

For a simple audit, suppose 80 requirements are approved, 72 have at least one linked test, and 60 have a passing result on the current released configuration. Structural test linkage is 72/80 = 90%, while supported verification closure is 60/80 = 75%. The latter is still not a universal assurance score because some requirements require multiple modes or methods and some links may be invalid. Different denominators answer different questions.

Evidence boundary. Store relationship type, source and target revisions, rationale, coverage domain, and reviewer. Use change-impact queries to find stale downstream evidence when requirements, interfaces, or models change. Merely maximizing edge count can reward meaningless connections; assess whether each link carries a valid engineering claim.
