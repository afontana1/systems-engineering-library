## The engineering situation

Model-based engineering fails when a tool repository is created without a method, semantic scope, viewpoints, ownership, queries, or generated products. The essential question is: **What model must be built, by whom, using which semantics and workflow, to answer which engineering and mission questions?**

The central idea of this chapter is **the method, language and tool are distinct**. Before a method is selected, the engineer must distinguish the decision being made, what evidence could falsify the leading approach, and which obligations cannot be relaxed. In the Northstar case, engineers, operators, safety leads and suppliers are accountable for different portions of one mission result. A locally successful artifact is not sufficient if the complete outcome is unsupported.

## Explanation: why the method works

A method specifies a modeling workflow, a language defines concepts and syntax, and a tool stores and manipulates representations. Semantic consistency comes from rigorous element meaning and relationships. A diagram may be syntactically legal but contradict a requirement or operational narrative.

A useful way to understand the mechanism is to follow the causal chain explicitly. Start with a stimulus or observed condition; ask which model connects it to the engineering outcome; identify the assumptions that let the model predict anything; and define the next decision. Avoid confusing a convenient dashboard measure with the actual mission variable. Where constraints are hard—such as safety authorization, configuration compatibility or accessibility—treat them as eligibility conditions before computing preferences.

**Deepening the reasoning — Semantic governance.** A machine-queryable model requires stable identifiers, relation types, ownership, units and consistent constraints. A drawing view can be helpful communication yet offer no queryable semantics. Track method-language-tool choices independently.

### Connect the theory to the course vocabulary

- Method defines the sequence and logic of engineering work; language defines concepts and relations; tool implements capabilities and repository behavior.
- A metamodel is an agreement about kinds of elements and relationships. It enables queries, validation, exchange, and governance.
- Viewpoints are stakeholder/question-specific specifications; views are generated or curated representations conforming to them.
- Identifiers should persist across views and transformations. Names can change; identity and provenance must remain controlled.
- The model plan should define generated products so the program does not recreate disconnected documents manually.

The statements above originate in the assigned course guide; use them as technical claims to test against a specific scenario, not as terminology to memorize. For each claim, ask what observation could show that it is false or inapplicable in the current design. The same discipline distinguishes an engineering argument from a procedural assertion.

## Deeper theory: a system model is a governed semantic commitment

### A diagram is a view, not the underlying system definition

Model-based systems engineering is valuable when distinct views refer to consistent underlying elements and relationships. A requirements view, a behavior view, and a physical architecture view may show different aspects of the same system; their consistency depends on identity, typing, and semantics, not visual similarity. If the “emergency priority request” appears in one diagram as a software message and in another as an operator approval, the model must state whether these are related events, alternatives, or incompatible interpretations. Merely putting both diagrams in one repository does not produce a coherent model.

A modeling method specifies the questions to answer, the needed representations, review criteria, and work sequence. A language specifies allowable model elements and semantics. A tool stores, checks, queries, and presents the model. Confusing these roles creates tool-centric programs that generate artifacts without useful engineering inference. For Northstar, the method may require a trace from emergency-access objectives through scenarios, functions, interfaces, hazards, and verification evidence. The language offers ways to express these relations; the tool is only as valuable as its ability to preserve their meaning and answer the intended queries.

### Typing and constraints enable stronger evidence than manual inspection

A model is a typed graph: nodes represent objects or concepts and edges represent relations whose permitted source and target types are defined. An allocation relation from a function to a component differs from a requirement-satisfaction claim or an information-flow link. A query such as “which critical functions have no allocated responsible constituent?” can be evaluated mechanically only if the relationship types and responsibility semantics are specified. A generic hyperlink labeled “related to” does not support the same assurance conclusion.

Well-formedness rules can enforce local invariants: every safety-critical function has an owner; a physical connector joins compatible interface types; units match across a parametric relationship; no retired configuration is presented as current. Semantic validity goes beyond syntactic compliance. A requirement linked to a test does not prove that the test measures the requirement's actual condition. Model reviews need to examine whether the relation is meaningful, whether negative cases are represented, and whether the evidence is appropriate to the hazard and intended use.

### View consistency is a change-propagation problem

A design change often affects several connected concerns. If a vehicle's door interlock moves from onboard hardware to a network-dependent service, changes can propagate to functional allocation, communication latency constraints, cybersecurity assumptions, operational modes, hazards, and test plans. A model can expose these dependencies through typed relationships, but it cannot guarantee that every important relationship has been captured. Automated impact analysis is most useful as a *candidate invalidation map*, followed by engineering review. Blindly treating every traced artifact as equally affected creates excessive false alarms; missing edges create dangerous false reassurance.

Configuration is essential. A simulation result produced for vehicle software release A, interface schema 2, and network assumptions X may not support a claim about release B with schema 3. Attach model elements and analyses to controlled configurations and provenance, not merely to a project name. Distinguish the authoritative source for each kind of information, because forcing all organizations into one database can create duplicate ownership and fragile synchronization. Federated sources can still support a coherent digital thread when identifiers, change processes, access rules, and semantics are governed.

### Abstraction must be fitted to the decision

The model does not need to describe every bolt, message, and human action at the same fidelity. It needs to preserve the distinctions relevant to its engineering questions. An early mission model may represent available transport capacity at aggregate level; a safety timing decision may require detailed state transitions, communication delays, and fault responses. Increasing detail without a clear decision question raises maintenance cost and may produce false confidence. Credibility comes from fit-for-purpose abstraction, reviewable assumptions, consistency checks, and configuration-specific evidence. The strongest MBSE program can explain both what the model establishes and what remains outside its boundary.

## Worked Northstar engineering case

The example starts with four disconnected artifacts: a mission-thread diagram, requirements spreadsheet, interface table, and test matrix. It defines a minimal information model linking MissionOutcome, MissionTask, Capability, System, Interface, Requirement, Measure, Model, Evidence, and Decision. Three queries replace manual reconciliation: unmet mission-task coverage, interfaces without verification evidence, and decisions based on superseded model versions.

Northstar models Request, Vehicle, DispatchPolicy and Availability as types with explicit properties and relations; a slide showing them as boxes is not a queryable semantic model unless the underlying relationships exist.

Work the example in two passes. First compute or trace the nominal outcome, naming the unit of analysis, released configuration and decision threshold. Second change one assumption, such as a degraded interface, heavier demand, invalid provenance or altered stakeholder constraint. If the recommendation changes, identify the threshold at which it changes; if it does not, explain the margin of robustness. A conclusion without its assumptions is not a reusable engineering result.

## A systematic check before accepting the result

1. **Boundary:** What part of the program, process or mission is represented, and what has been excluded?
2. **Evidence:** Which observations, versions, or tests support the premises, and what remains hypothetical?
3. **Causality:** Could the proposed mechanism be confused with a proxy, confounding condition or common dependency?
4. **Decision:** Which alternatives are still feasible, who has authority, and what would force reconsideration?
5. **Assurance:** Which safety, security, accessibility or quality guardrail cannot be traded for speed or convenience?

### Counterexample and failure boundary

Tool export compatibility does not guarantee model meaning survives translation.

Write a minimal typed graph for request-to-vehicle dispatch and detect one deliberately invalid relationship. Notice that a mathematically consistent answer can still be an inappropriate decision if the intended use or validity assumptions have changed. In professional work, a responsible engineer records that limitation alongside the nominal result.

## Practise the explanation, not just the procedure

1. **Concept check:** Distinguish MBSE method, language, tool, metamodel, model, view, viewpoint, repository, and generated artifact. **Explain:** Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
2. **Concept check:** Define model scope, purpose, questions, stakeholders, products, queries, packages, and governance. **Explain:** Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
3. **Concept check:** Select a SysML v2 or v1.7 path and document semantic/interchange limitations. **Explain:** Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
4. **Sensitivity exercise:** Recalculate or re-evaluate the Northstar case after changing one major assumption. State the original and revised decision.
5. **Transfer exercise:** Apply **semantic governance** to a different engineering system (hospital scheduling, power distribution, or emergency communications). Describe what remains transferable and what does not.

### Explained response guide

- A strong answer separates the mission outcome from the internal activity metric, states which evidence is authoritative, and specifies an escalation or stop rule when evidence becomes stale.
- For the sensitivity exercise, **Write a minimal typed graph for request-to-vehicle dispatch and detect one deliberately invalid relationship.** The correct answer is conditional on the chosen assumption and its justification; there is no single universally preferred architecture or process.
- For the transfer exercise, preserve the causal logic but redefine the boundary, user population, constraints, measurements, and physical limitations. Copying Northstar numbers into another domain would be invalid.

### A metamodel is a set of falsifiable relationship commitments

The course's original MBSE plan emphasizes method, language, tools and viewpoints. The NS-DME16.1 extension supplies a controlled **toy metamodel** to make those commitments executable. In the [graph input](../case/controlled-inputs.json), a requirement can be `allocated_to` a function, a function `realized_by` a component, a requirement `checked_by` a test, and a test can have `produced` evidence. The script rejects a direct `requirement produced evidence` relation because its endpoint types violate the defined semantics. This is not a SysML parser, interchange standard, or proof system.

Let a graph be \(G=(V,E,\tau,\rho)\), where \(\tau(v)\) is node type and \(\rho(e)\) is relation type. A typing rule has the form

\[
\forall (x,\texttt{checked\_by},y)\in E:\quad \tau(x)=\texttt{requirement}\ \land\ \tau(y)=\texttt{test}.
\]

The rule can be checked against every edge, but it says nothing about whether the test is meaningful. The same test might be attached to an unrelated requirement. Correct engineering semantics need review of test intent, methods, acceptance criteria and evidence contents. Formal well-formedness is a *necessary filter*, not sufficient assurance.

**Worked graph baseline:** Five requirements each have a path through function/component and test/evidence. The resulting five records in [trace-quality.csv](../case/trace-quality.csv) are configuration-current for the bounded `course-screening` use. Their `operationally_qualified` values are all **false**. The configuration completeness ratio \(5/5=1.0\) refers only to these explicit rules, not to all program requirements or genuine coverage. This distinction prevents coverage statistics from being mistaken for evidence of requirements satisfaction.

Model planning should include stable IDs, naming conventions, controlled revisions, explicit units, viewpoints for mission and system decisions, expected relation semantics, independent queries, and change propagation. Maintain different authorities for system structure, threat models, supplier interface definitions, test observations and mission operations. “Single source of truth” is too coarse when these records have different owners and validity windows.

**Worked malformed-model test.** If the input repeats `R-ACCESS`, the validator raises `ValueError` rather than silently overwriting one record in an index. If an edge points to `C-UNKNOWN`, it also fails. A duplicate can corrupt a graph even when every rendered diagram looks plausible. Both cases appear in the regression suite as deliberate negative data.

**Explained exercise.** Propose a `satisfies` edge from component `C-ACCESS` to `R-ACCESS`. Is the existing allocation path enough to claim satisfaction? No. A formally defensible satisfaction claim also needs operating conditions, acceptance criteria, evidence revision, test applicability, and an authorized reviewer. Add a separate claim node or typed relation carrying that argument; do not relabel an allocation arrow as proof. Connect the new claim's credibility to the Week 3 VV&A plan and the Week 8 digital thread.
