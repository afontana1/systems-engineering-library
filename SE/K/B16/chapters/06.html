Teaching purpose. The guide defines the assessed engineering deliverable. This chapter builds the underlying mental model and practices reasoning before the lab. All Northstar program details and calculations below are fictional teaching cases, not operational claims.

The engineering situation

The value of an integrated model is demonstrated by the questions it can answer and the decisions it can improve. The essential question is: Can the Northstar model produce reproducible analysis, reveal inconsistencies, and support a decision better than disconnected artifacts?

The central idea of this chapter is analysis closes the loop between model and decision. Before a method is selected, the engineer must distinguish the decision being made, what evidence could falsify the leading approach, and which obligations cannot be relaxed. In the Northstar case, engineers, operators, safety leads and suppliers are accountable for different portions of one mission result. A locally successful artifact is not sufficient if the complete outcome is unsupported.

Explanation: why the method works

Parameter relationships can be derived and executed, but every numerical result requires units, assumptions, sensitivity and a decision threshold. Analyses should fail loudly when a parameter is missing or its version is incompatible with the architecture.

A useful way to understand the mechanism is to follow the causal chain explicitly. Start with a stimulus or observed condition; ask which model connects it to the engineering outcome; identify the assumptions that let the model predict anything; and define the next decision. Avoid confusing a convenient dashboard measure with the actual mission variable. Where constraints are hard—such as safety authorization, configuration compatibility or accessibility—treat them as eligibility conditions before computing preferences.

Deepening the reasoning — Parametric units and uncertainty. Range=energy/consumption is meaningful only when numerator and denominator use compatible units and conditions. Propagate bounded input uncertainty before asserting feasibility. Threshold crossing is a decision question, not merely a value recalculation.

Connect the theory to the course vocabulary

  • Analytics include structural queries, coverage matrices, graph paths, calculations, simulations, sensitivity, and generated reports.
  • Queries should have controlled definitions, test cases, expected results, failure behavior, and version compatibility.
  • Change impact is a graph/reasoning problem: a change propagates through semantics, allocations, interfaces, analyses, evidence, decisions, and products.
  • Automated reports are only trustworthy when source authority, transformation logic, query version, and configuration are recorded.
  • Case studies should be analyzed for actual decision improvement, not retold as success stories.

The statements above originate in the assigned course guide; use them as technical claims to test against a specific scenario, not as terminology to memorize. For each claim, ask what observation could show that it is false or inapplicable in the current design. The same discipline distinguishes an engineering argument from a procedural assertion.

The mechanism beneath the method

Model-based analytics converts semantic model relationships into calculations and change-impact queries.

Distinguishing related ideas

An executable parametric calculation is only as credible as the parameters, units and system configuration it references.

Interpretation and boundary conditions

Analytic automation should expose data lineage and invalid assumptions rather than simply produce a highly precise result.

Graduate depth: model-based analytics as a chain from semantics to decisions

Analytics quality is limited by the modeled question

Model-based analytics connects structured engineering representations to calculations, trade studies, and decision evidence. Its benefit is not that diagrams can automatically generate charts. It is that inputs, constraints, relationships, and outputs can be associated with identifiable architecture elements and controlled versions. A calculation must declare the population, operating modes, units, configuration, and uncertainty it represents. A simulation that correctly calculates the wrong mission quantity can be less useful than a simpler model that clearly addresses the decision.

Suppose a capacity model predicts maximum trips per hour from fleet size, charging time, boarding duration, and dispatch rules. A parametric constraint might approximate usable_hours = fleet_count * shift_hours * availability, with availability derived from maintenance and charging assumptions. The expression is dimensionally consistent but may double-count limitations if charging is already included in availability. Traceability to the source of each factor exposes this error. A stronger analysis represents bottlenecks, shared resources, and changing modes explicitly, then checks simplified approximations against the richer model where appropriate.

Uncertainty propagation and model applicability

If output y=f(x_1,...,x_n) depends on uncertain input vector x, a local linear approximation gives Var(y) approx J Sigma J^T, where J is the row vector of partial derivatives and Sigma is the input covariance matrix. This approximation requires differentiability near the evaluation point and tolerable linearization error. It cannot reliably describe threshold failures, discontinuities, or heavy-tailed disturbances. Sampling-based propagation may handle those cases better, provided the joint input distribution and dependencies are justified. Neither method captures uncertainty from omitted causal structure unless that uncertainty is represented separately.

A model's credibility should be tied to a decision and operating envelope. Evidence that a thermal model matches benign laboratory tests does not automatically justify extrapolating to high-altitude hot-weather operations. Maintain an applicability record that states validated configurations, regimes, measurement uncertainty, structural limitations, and checks against data not used for calibration. When combining models, take the intersection of their compatible assumptions rather than presuming the broadest advertised range of each is safe.

Results need an argument, not just a dashboard

A Northstar trade study might find that twelve vehicles meet expected peak demand while eleven reduce lifecycle cost. The relevant evidence includes the demand distribution, service-level constraint, maintenance availability, passenger-class effects, and uncertainty in model parameters. If the 95th-percentile accessible-trip wait is the actual mission criterion, optimizing average fleet utilization is a proxy and can be misleading. The decision artifact should show objective, feasible alternatives, sensitivity, margins, and the evidence that would reverse the recommendation.

Digital engineering improves this reasoning when change propagates transparently from requirement to architecture element to computation to result. It degrades reasoning when a red/green dashboard hides unverified assumptions, stale data, or incomplete model synchronization. Treat a model-based analytic result as a versioned claim with explicit premises, not a self-validating number produced by trusted software.

Worked Northstar engineering case

A query reports 100% requirement verification coverage, but the example discovers that 12 verification cases point to superseded identifiers and two tests use an old interface version. The worked analysis distinguishes syntactic link coverage from valid evidence coverage and generates a corrected decision dashboard with uncertainty and stale-data warnings.

For a vehicle with 24 kWh usable energy at 0.32 kWh/km, nominal range is 75 km. At 0.40 kWh/km under adverse conditions it is 60 km; a 65 km duty cycle is no longer feasible.

Work the example in two passes. First compute or trace the nominal outcome, naming the unit of analysis, released configuration and decision threshold. Second change one assumption, such as a degraded interface, heavier demand, invalid provenance or altered stakeholder constraint. If the recommendation changes, identify the threshold at which it changes; if it does not, explain the margin of robustness. A conclusion without its assumptions is not a reusable engineering result.

A systematic check before accepting the result

  1. Boundary: What part of the program, process or mission is represented, and what has been excluded?
  2. Evidence: Which observations, versions, or tests support the premises, and what remains hypothetical?
  3. Causality: Could the proposed mechanism be confused with a proxy, confounding condition or common dependency?
  4. Decision: Which alternatives are still feasible, who has authority, and what would force reconsideration?
  5. Assurance: Which safety, security, accessibility or quality guardrail cannot be traded for speed or convenience?

Counterexample and failure boundary

A parametric value with no unit or environmental bound is dangerous precision.

Calculate range in favorable and adverse conditions; state whether a 65 km duty cycle survives the bound. Notice that a mathematically consistent answer can still be an inappropriate decision if the intended use or validity assumptions have changed. In professional work, a responsible engineer records that limitation alongside the nominal result.

Practise the explanation, not just the procedure

  1. Concept check: Design and execute model queries, matrices, calculations, and generated reports. Explain: Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
  2. Concept check: Connect descriptive model elements to analytic models, data, uncertainty, and decision criteria. Explain: Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
  3. Concept check: Perform change-impact analysis across mission, requirements, architecture, interfaces, simulations, tests, and decisions. Explain: Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
  4. Sensitivity exercise: Recalculate or re-evaluate the Northstar case after changing one major assumption. State the original and revised decision.
  5. Transfer exercise: Apply parametric units and uncertainty to a different engineering system (hospital scheduling, power distribution, or emergency communications). Describe what remains transferable and what does not.

Explained response guide

  • A strong answer separates the mission outcome from the internal activity metric, states which evidence is authoritative, and specifies an escalation or stop rule when evidence becomes stale.
  • For the sensitivity exercise, Calculate range in favorable and adverse conditions; state whether a 65 km duty cycle survives the bound. The correct answer is conditional on the chosen assumption and its justification; there is no single universally preferred architecture or process.
  • For the transfer exercise, preserve the causal logic but redefine the boundary, user population, constraints, measurements, and physical limitations. Copying Northstar numbers into another domain would be invalid.

Executable queries should return evidence gaps, not cosmetic coverage

An analytic query is a reproducible mapping from a versioned information model to a decision-relevant exception or measure. The case provides three kinds: path completeness, revision compatibility, and impact reachability. These are stronger than counting diagrams but remain limited to what their schema represents. The code explicitly tests edge validity and the current intended use before reporting results.

Query 1 — completeness. For each requirement \(r\), search for an allocated_to function with realized_by component and a checked_by test with produced evidence. Let \(I_r=1\) only if all paths exist and the linked evidence passes revision checks. The mean screen completeness is

\[ C=\frac{\sum_{r\in R} I_r}{|R|}. \]

On revision 1.0 the case shows \(C=5/5=100\%\). After the dispatch supplier changes interface to 2.0 without retesting, only four of five records remain current, giving \(C'=4/5=80\%\). Neither value is the ratio of requirements satisfied by field tests; that denominator and evidence class are not available.

Query 2 — change impact. impact(cfg,'IF-DISPATCH') returns T-COMMS, E-COMMS, R-COMMS and DEC-MISSION-16. It traverses intentionally specified relation directions, so it neither guarantees transitive completeness across an enterprise nor discovers implicit physical correlations. A production thread should check missing edges, cross-repository links, deleted nodes, semantic mappings and human review dependencies.

Query 3 — authorized use. get_artifact tests both role clearance and the object's authority_for list. Being able to read a restricted model does not confer authority to use it for release. This is a common but serious error when analytics dashboards combine metadata from many systems.

Worked query verification. Recompute trace-quality.csv from source JSON and compare rows to the packaged baseline. Change only the interface revision, leave the evidence unchanged, and verify the expected one failed path. Then update the evidence and repeat only after the new interface is technically reviewed; in a real program, do not automatically write result: pass simply to turn a query green.

Explained exercise. If a team adds five orphan requirements without tests but keeps the original five tested requirements, how much does the simplified score change? With ten requirements and five current paths, \(C=5/10=50\%\). Explain why an analysis based on the old five-record subset would deceptively preserve 100%. An actual audit must also assess whether the ten requirements are complete, nonduplicative and appropriately scoped.

Limitations. This graph does not evaluate SysML constraints, test procedure adequacy, logical satisfiability, measurement uncertainty, or supplier attestations. A meaningful analytics review exhibits false positives and false negatives, not merely a successful script exit code.
