## The engineering situation

A model-based method should transform stakeholder and mission concerns into coherent behavior, requirements, architecture, interfaces, and measures. The essential question is: **Can the model explain how Northstar contributes to mission outcomes without collapsing mission, capability, and system levels?**

The central idea of this chapter is **a model should answer queries, not just show drawings**. Before a method is selected, the engineer must distinguish the decision being made, what evidence could falsify the leading approach, and which obligations cannot be relaxed. In the Northstar case, engineers, operators, safety leads and suppliers are accountable for different portions of one mission result. A locally successful artifact is not sufficient if the complete outcome is unsupported.

## Explanation: why the method works

Use behavior, structure, requirements and allocations to answer traceability and design questions. Determine which system functions satisfy mission needs and which physical elements implement them. Introduce views as projections of one controlled semantic baseline.

A useful way to understand the mechanism is to follow the causal chain explicitly. Start with a stimulus or observed condition; ask which model connects it to the engineering outcome; identify the assumptions that let the model predict anything; and define the next decision. Avoid confusing a convenient dashboard measure with the actual mission variable. Where constraints are hard—such as safety authorization, configuration compatibility or accessibility—treat them as eligibility conditions before computing preferences.

**Deepening the reasoning — Structural and behavioral closure.** An allocation should connect required functions to components and behavior and tests. Cross-view consistency requires checking state transitions, activity flows and interface ownership together. Configuration is part of semantic meaning.

### Connect the theory to the course vocabulary

- OOSEM is used here as a reasoning flow, not as a rigid universal process.
- Mission tasks describe what must occur in the mission; capabilities describe the ability needed; system functions describe what a system does; components implement behavior.
- Logical architecture should remain solution-neutral long enough to preserve alternatives and expose dependencies.
- State and degraded-mode models are essential when mission outcomes depend on synchronization, communications, power, operator authority, or recovery.
- Model validation includes semantic and cross-view consistency, not merely syntax.

The statements above originate in the assigned course guide; use them as technical claims to test against a specific scenario, not as terminology to memorize. For each claim, ask what observation could show that it is false or inapplicable in the current design. The same discipline distinguishes an engineering argument from a procedural assertion.

### SysML and OOSEM separate engineering reasoning from notation

SysML supplies a vocabulary for representing structure, behavior, requirements, and constraints; OOSEM supplies a way to organize analysis of needs and derive architecture. The distinction matters because a diagram does not dictate the questions engineers should ask. A block diagram may be internally consistent while the chosen operational scenario omits a critical exception. A method guides where to seek evidence; a language makes the resulting relations more precise and exchangeable.

An object-oriented systems model is not necessarily a software class design. Logical elements express system responsibilities that might later be fulfilled by hardware, people, software, or external organizations. A useful model should preserve traceable transformations from mission analysis to functions, interfaces, and candidate solutions. Model consistency rules support that chain, but technical review must still challenge whether the selected abstractions capture the causal mechanisms and constraints relevant to intended use.

## Graduate depth: SysML viewpoints as linked engineering assertions

### Model structure must answer a defined question

SysML provides a language for representing system requirements, structure, behavior, parametric relations, and their connections. The existence of a diagram does not establish completeness or correctness. A structural view answers which parts and ports are assumed to exist; an activity or state view expresses ordering and conditions; a requirement relation makes a claim about allocation or satisfaction. These are different kinds of assertions, with different validation obligations. Lightweight OOSEM-style reasoning is valuable because it moves deliberately from stakeholder needs and operational scenarios to logical behavior and candidate physical structures, rather than drawing hardware blocks first and declaring them the solution.

A system model may be treated as a typed graph `G = (V,E,T)` whose nodes represent model elements, edges represent typed relations, and `T` is a set of well-defined semantic constraints. A requirement-to-function allocation and a function-to-component allocation need not imply that the component satisfies the requirement. Satisfaction also requires evidence about performance under operating conditions. Likewise, a «trace» relation records association; it does not mean that the source logically entails the target. Conflating association, derivation, verification, and satisfaction is a common failure of model-based governance.

### Consistency across viewpoints is a testable property

Consider a Northstar dispatch behavior described by an activity diagram and realized by software and vehicle subsystems. A sequence can depict an accessible-trip request as accepted, assigned, and acknowledged. The structural model must provide an interface for each exchange; the state model must specify what happens if acknowledgement never arrives; the requirement model must state the acceptable degraded behavior. A diagram can be individually well-formed while these cross-view claims conflict. Consistency checks therefore connect state and behavior to interface contracts and physical allocations.

Formalized constraints can expose some contradictions. For example, an invariant `assigned_trip_count <= available_vehicle_count` might be appropriate for a simplified model with one active assignment per vehicle, but it fails when reservations are scheduled for later time windows. The condition must state temporal scope and resource semantics before it becomes a valid rule. Similarly, ports labelled in different units require conversion rather than string matching. Automated model rules are most useful when engineers can explain their assumptions and test counterexamples, not when a large rule count is used as a proxy for model validity.

### Abstraction, viewpoints, and decision evidence

The model should be as detailed as required by its intended decisions. An operational analysis may need passenger demand, service regions, and fallback policy but not detailed motor-winding geometry. A thermal risk study may need winding losses and cooling dynamics but only a simplified dispatch demand profile. Both views can legitimately abstract the same system differently. The integration challenge is to preserve the shared quantities and conditions that make the views comparable.

Versioned viewpoints should document the question answered, abstraction boundary, data sources, units, ownership, and known omissions. A model review can then ask whether the architecture is *consistent*, whether key needs are *covered*, and whether relevant performance claims are *supported by independent evidence*. These are complementary criteria. A coherent SysML package is a valuable reasoning tool, but it does not become an operational truth source until its use-specific claims are tested against reality.

## Worked Northstar engineering case

The mission task “Maintain accessible evacuation mobility” is decomposed into detect demand, prioritize riders, allocate capacity, communicate assignment, transport, and confirm completion. The example maps capabilities and participating systems without prematurely assigning all behavior to Northstar vehicles. A degraded-communications state model shows local fallback, delayed reconciliation, and evidence gaps.

A request-cancellation state change must trace to an API behavior contract, dispatcher component, and fault tests. If the model says cancellation is allowed from Completed, the inconsistency should be detectable by rule.

Work the example in two passes. First compute or trace the nominal outcome, naming the unit of analysis, released configuration and decision threshold. Second change one assumption, such as a degraded interface, heavier demand, invalid provenance or altered stakeholder constraint. If the recommendation changes, identify the threshold at which it changes; if it does not, explain the margin of robustness. A conclusion without its assumptions is not a reusable engineering result.

## A systematic check before accepting the result

1. **Boundary:** What part of the program, process or mission is represented, and what has been excluded?
2. **Evidence:** Which observations, versions, or tests support the premises, and what remains hypothetical?
3. **Causality:** Could the proposed mechanism be confused with a proxy, confounding condition or common dependency?
4. **Decision:** Which alternatives are still feasible, who has authority, and what would force reconsideration?
5. **Assurance:** Which safety, security, accessibility or quality guardrail cannot be traded for speed or convenience?

### Counterexample and failure boundary

Model completeness is relative to purpose, not the quantity of diagrams.

Detect an invalid Completed→Cancelled transition and trace the change to state, requirement and test records. Notice that a mathematically consistent answer can still be an inappropriate decision if the intended use or validity assumptions have changed. In professional work, a responsible engineer records that limitation alongside the nominal result.

## Practise the explanation, not just the procedure

1. **Concept check:** Apply a lightweight OOSEM flow from stakeholder and mission analysis through logical and physical architecture. **Explain:** Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
2. **Concept check:** Construct SysML representations of requirements, behavior, structure, interfaces, states, measures, analysis, and verification. **Explain:** Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
3. **Concept check:** Separate mission tasks and capability needs from system functions and design elements. **Explain:** Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
4. **Sensitivity exercise:** Recalculate or re-evaluate the Northstar case after changing one major assumption. State the original and revised decision.
5. **Transfer exercise:** Apply **structural and behavioral closure** to a different engineering system (hospital scheduling, power distribution, or emergency communications). Describe what remains transferable and what does not.

### Explained response guide

- A strong answer separates the mission outcome from the internal activity metric, states which evidence is authoritative, and specifies an escalation or stop rule when evidence becomes stale.
- For the sensitivity exercise, **Detect an invalid Completed→Cancelled transition and trace the change to state, requirement and test records.** The correct answer is conditional on the chosen assumption and its justification; there is no single universally preferred architecture or process.
- For the transfer exercise, preserve the causal logic but redefine the boundary, user population, constraints, measurements, and physical limitations. Copying Northstar numbers into another domain would be invalid.
