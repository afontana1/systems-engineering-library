## Conceptual explanation

### Five questions that should not be blended
**Implementation:** was each element made to its design? **Integration:** can the elements work together through defined interfaces? **Verification:** does the realized system meet specified requirements? **Validation:** does it serve intended use in a representative setting? **Acceptance:** has the authorized customer accepted delivery against the agreed basis? These are related but different decisions. A component test can satisfy a low-level requirement while leaving an operational need unvalidated.

Integration planning should follow dependency and risk, not just convenience. Test high-uncertainty interfaces early with stubs, simulators or prototype elements, then expand to end-to-end integration. Specify integration order, interface versions, required test assets and environment controls, failure triage, and evidence preservation. Later tests cannot reliably repair a missing record of which versions were assembled.

### Designing evidence backwards
Start with the requirement, define the exact pass/fail rule, select verification method, specify stimulus and measurement, and identify configuration and environmental coverage. Then ask what validation scenarios demonstrate that users actually get the promised benefit. For safety or high consequence, an observed zero-failure sample may not establish that true failure probability is acceptably low. Statistical confidence, hazard analysis and independent assurance may be necessary.

### Transition is a system event
Operational readiness includes trained operators, accessible procedures, maintenance spares, cybersecurity responsibilities, monitoring, emergency services, support contracts, rollback mechanisms and data stewardship. A technically verified product can fail in operations because enabling systems and personnel were omitted from readiness planning.

### Build an evidence matrix
Each row has requirement ID, item/version, method, procedure, required environment, expected result, actual result, deviation reference, reviewer and acceptance decision. Link validation evidence to scenarios and stakeholder needs. Separate design validation, operational validation and formal customer acceptance when the program uses distinct authorities.

## Worked example: reason through the case

**Example:** Req R-22: 'After loss of dispatch connectivity, vehicle shall enter defined safe state within 3 seconds.' Unit test injects simulated message loss into control software. Integration test disables the actual network between dispatch and prototype vehicle. System verification repeats under defined speed/load conditions. Operational validation checks whether passengers and operator can manage the degraded event safely. Acceptance requires the customer-approved evidence set and operating restrictions.

## Retrieval and transfer practice

1. A route app passes its functional tests but users cannot complete a journey in poor connectivity. Which evidence is missing?
2. Write an integration sequence for dispatch, onboard controller and passenger app.
3. Name four nontechnical artifacts necessary for operational transition.

<details>
<summary><strong>Reveal explained answers after attempting the problems</strong></summary>

1. The design may be verified to its narrow requirements, but intended-use validation, degraded-network requirements, and relevant end-to-end tests are missing.

2. First check each interface against a stub; then dispatch-controller contract and failure behavior; then app-dispatch flows; then full trip scenarios including disconnect and rollback, preserving versioned logs.

3. Operator training, maintenance instructions, incident response plan, customer support/communications, accessibility procedures, service ownership, spare parts and authority to restrict operations.

</details>

## A failure mode to recognize

Mistake: equating "all test cases passed" with "the service will achieve its mission".
