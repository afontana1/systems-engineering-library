## Conceptual explanation

### A function names a transformation
A function describes something the system must do to transform an input, event or state into an outcome. It does not name the part that eventually performs it. 'Detect an approaching pedestrian' is a function; 'lidar sensor' is a possible physical design choice. Preserving the distinction prevents early hardware assumptions from dictating requirements. A functional architecture maps interactions and dependencies among functions, while a product/physical architecture maps implementation elements.

Decompose a top-level service capability into functions until allocation and verification decisions become tractable. Decomposition should be collectively sufficient but avoid overlapping responsibilities. For shuttle operation: accept ride request; decide service eligibility; plan assignment; navigate route; monitor hazards; respond to emergencies; report status. Each function has input/output and control data, relevant modes and failure responses. A list of verbs without flows or conditions is not enough.

### Behavior is temporal
Functional decomposition describes what must happen; sequence, state, timing and concurrency models clarify *when and under which conditions*. Build a small state machine: unavailable → ready → boarding → operating → stopped → recovering. For every transition, name its event and guard condition. Ask what happens to commands arriving in a forbidden state. A 'start motion' command that can be accepted during manual maintenance is a design hazard. State invariants are properties that must hold across all behavior in a given state.

**Functional-flow reasoning:** An apparently simple event such as 'passenger presses emergency stop' crosses recognition, arbitration, command transmission, braking actuation, status indication and recovery authorization. The end-to-end response time is approximately the sum of dependent stage latencies (plus possible queueing). If a response objective is 500 ms, allocating 250 ms to sensing, 200 ms to messaging and 150 ms to actuation already exceeds the budget—even before margins.

### Functional completeness tests
Walk a nominal and three off-nominal scenarios through the model. Identify missing entry/exit conditions, external triggers, data losses and recovery paths. Mark functions with no requirement source and requirements with no behavioral realization. Do not infer reliability from a clean diagram: test the difficult transitions.

## Worked example: reason through the case

**Worked timing budget (illustrative):** Detection 90 ms + classification 110 ms + arbitration 50 ms + communication 80 ms + brake command activation 60 ms = 390 ms. A requirement to *initiate* braking within 500 ms leaves 110 ms nominal margin, but worst-case jitter and missed messages could consume it. To establish compliance, specify worst-case bounds, concurrency, clock basis and test conditions. A 390 ms average is insufficient to prove a 500 ms maximum.

## Retrieval and transfer practice

1. Decompose "deliver a passenger safely" into five implementation-neutral functions.
2. A system is in the MAINTENANCE state. Which transition guard prevents inadvertent departure?
3. The worst-case latencies are 140, 170, 80 and 150 ms. Does the 500 ms bound hold?

## A failure mode to recognize

Mistake: equating a product breakdown with a functional breakdown; this hides options and creates circular reasoning.
