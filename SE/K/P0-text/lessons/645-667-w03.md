## Conceptual explanation

### Structure the work around deliverables
A Work Breakdown Structure (WBS) is a hierarchical decomposition of the work required to deliver project scope, ordinarily organized around products and major deliverables. It should cover all approved scope exactly once at each level: the **100% rule**. Use a dictionary to define each element's boundaries, deliverables, completion evidence, assumptions and exclusions. A WBS containing only activities such as 'meetings', 'review' and 'code' cannot reliably show what complete scope has been delivered.

Distinguish a PBS, which depicts products and subsystems, from a WBS, which organizes work to create the authorized deliverables. Verification, training and documentation may be WBS scope even when they are not shuttle subsystems. A *control account* joins scope, cost and schedule under accountable management. Below it, work packages have measurable completion criteria, budgets and planned dates; planning packages reserve future work not yet decomposed in detail.

### From breakdown to authorization
A work authorization identifies what team may start, under which baseline, budget, schedule and acceptance criteria. It protects the project from uncontrolled effort and unclear promises. The control-account manager must be able to reconcile WBS scope with the integrated schedule and cost estimate. If a change adds work, it should pass impact review before entering the performance baseline.

### Evidence of completion
Percent complete must be grounded in observable milestones or physical progress. 'Software integration is 90% complete' is suspect if completion means passing the full cross-system regression suite and no integrated test has run. Prefer discrete earning rules tied to documented progress. Use internal milestones with value proportional to actual accomplished scope rather than optimism.

### Quality check
Review sibling elements for overlaps and omissions; verify that every required deliverable has a WBS owner, budget, schedule activities and acceptance evidence. Then check reverse trace: budgeted work that does not contribute to an authorized deliverable may indicate inefficiency or scope drift.

## Worked example: reason through the case

**Example WBS:** 1.0 Shuttle Pilot → 1.1 Vehicles, 1.2 Dispatch System, 1.3 Campus Interfaces, 1.4 Integration and Verification, 1.5 Operations Readiness. Under 1.3: 1.3.1 Stops and Signage, 1.3.2 Campus Network Interface. The dictionary for 1.3.2 explicitly includes network-contract specification, environment test, cybersecurity review and acceptance evidence; it excludes campus backbone replacement unless separately authorized.

## Retrieval and transfer practice

1. Classify "automated braking module", "write software" and "system test campaign" in PBS versus WBS.
2. Name four minimum fields for a WBS dictionary entry.
3. A work package reports 80% complete without deliverable evidence. What should a reviewer ask?

<details>
<summary><strong>Reveal explained answers after attempting the problems</strong></summary>

1. Braking module is a PBS product; software development work belongs in WBS deliverable scope; system test campaign is WBS scope with defined test deliverables, though not necessarily a physical PBS element.

2. ID/name, scope and exclusions, deliverable, accountable owner, completion/acceptance evidence, assumptions, and dependencies.

3. Ask for objective earning rules: passed test set, accepted interface build, reviewed documents or measurable units. Reassess earned progress if evidence does not exist.

</details>

## A failure mode to recognize

Mistake: using an unstructured task list to define scope; the WBS should preserve product accountability as activities change.
