Conceptual explanation

Avoid the single-cause story

Complex accidents are often described with one memorable proximate fault. Such stories are useful only if they do not hide failed defenses. The Mars Climate Orbiter mission was lost after a ground software units mismatch contributed to navigation errors. NASA investigations also identified failures in communication, operations preparation and systems engineering controls. The lesson is not merely 'convert units'; it is to make assumptions testable at boundaries, monitor anomalies, and create escalation routes that work when people notice something surprising.

Separate trigger or proximal event from underlying conditions that made it possible and from missing detection or recovery barriers. Build a causal map with branches for technical design, verification, information flow, governance, operational workload and response. Use evidence-based claims. Do not invent details about a historical accident to fit a preferred framework.

Challenge an engineering argument

A red team should ask which assumptions, interfaces and unlikely conditions could defeat an apparently reasonable design. Useful prompts include: What if the environment differs from test conditions? What if a producer emits correct-looking data in wrong units? What if a required warning is ignored because no single owner can act? What if independent controls secretly depend on the same network or clock?

Defense in depth without illusion

Layers are only independent when common-cause failures are addressed. Two safety monitors reading the same corrupted source do not provide fully independent protection. For each claimed defense, state its trigger, failure coverage, independence assumptions, test method and escape path. Test off-nominal transitions rather than only component happy paths.

Turning learning into preventive action

Map each credible failure pathway to prevention, detection, containment or recovery. Every corrective action should name an owner, controlled process or design change, measurable acceptance evidence and audit of effectiveness. An awareness presentation is not a substitute for correcting an unsafe interface contract.

Worked example: reason through the case

Illustrative shuttle near miss: The map service publishes coordinates in degrees; the planner expects radians. The command passes schema validation because both fields are floating-point. Vehicle drifts toward a prohibited zone. Stronger controls include typed unit metadata, automated interface contract tests, plausibility bounds, independent geofencing and abnormal-event escalation. An incident report that blames only the programmer misses the missing system-level protections.

Retrieval and transfer practice

  1. Name a proximate cause and two systemic contributors in a wrong-units incident.
  2. Why may two monitors not provide independent assurance?
  3. Write a corrective action with evidence for an ambiguous coordinate field.

A failure mode to recognize

Mistake: explaining a socio-technical failure as one human mistake while overlooking controls that should have caught it.
