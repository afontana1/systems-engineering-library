Knowledge lenses for this course

  • Model, method, language, tool, and repository — A model is a purposeful representation of a system for answering questions.
  • Architecture views, viewpoints, and consistency — A viewpoint defines conventions and concerns for seeing a system; a view applies those conventions to a particular system.
  • Requirements traceability and impact analysis — Traceability is a justified network of relationships among needs, requirements, functions, design elements, tests, risks and decisions.
  • Stakeholders, needs, and value — A stakeholder is anyone with a legitimate interest in, effect on, or consequence from a system.
  • Functional, logical, and physical architectures — Functional architecture describes what transformations and behaviors must occur, independent of which hardware or software will perform them.
  • Verification cross-reference matrices and test design — A verification cross-reference matrix (VCRM) links each controlled requirement to verification method, level, procedure, success criterion, configuration and evidence.

Direct behavior and model-query method

Use state contracts, invariants, and bounded model checking for behavioral modeling and model-quality analysis. Students can reproduce the duplicate-assignment counterexample without a commercial modeler. Connect the result to typed requirements/evidence semantics and to the approved model baseline; no SysML conformance is asserted by the Python teaching checker.

Phase 3 technical reference: Direct model constraints and executable checks

Use the software-model invariant and OCL example for automated cross-object consistency checks alongside the existing finite-state behavioral modeling guide. Explain what each formalism actually expresses and what its checking tool does not establish.

Phase 4 technical reading: Validated links are not validated behavior

For weeks 10–12, the model audit and semantic constraints guide gives a typed requirements–components–controls–evidence graph and runs an executable configuration check. It detects four stale references when fictional CM-B2 changes to CM-B3. Students must distinguish this JSON educational checker from a conformant SysML v2 parser and from full evidence adequacy.

Phase 5 technical reading: A normative model requires normative tool checks

For the modeling-plan and structure weeks, the SysML v2 textual guide demonstrates part def versus typed usage and a separate CSV-to-baseline trace auditor. An actual conforming implementation must parse, resolve and version the model before its syntax can be treated as validated; the teaching Python code is not that implementation.

Best supporting shelf for this course

  • Guide to the Systems Engineering Body of Knowledge — Breadth-first conceptual encyclopedia and pointers to further references.
  • OMG SysML formal specifications — Precise notation and semantics; consult when you need authoritative modeling constructs; not a beginner textbook.
  • OMG UML formal specification — Formal language definition for software structure, interaction and behavior models.
  • CMU SEI: Early Analysis of Software Architecture — Detailed quality-attribute and architectural reasoning studies.
  • NIST SP 800-160 Rev. 1 — Engineering Trustworthy Secure Systems — Security and trustworthiness integrated with engineering lifecycle reasoning.
