MBSE · W01

MBSE value, model purpose, and the document-to-model transition

Companion chapter: EN.645.631, Week 01 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 1 for assignment, assessment criteria and complete reading plan.
Concepts: model purpose, model authority, source of truth, digital thread
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How can a model reduce uncertainty instead of merely reproducing documents?

Conceptual tutorial

Models are decision instruments

A model is a selective representation of a system, designed for a purpose. A commuter map is useful because it suppresses building details while preserving connected stations. A system model similarly retains requirements, behaviors, interfaces, physical elements and their relations at a degree of precision suited to the decisions it supports. A beautiful diagram that cannot answer a requirements-change question may be less useful than a humble, queryable table.

Distinguish the model (elements with identities, attributes, semantics and relationships), a view (a purpose-specific presentation of a subset of the model), and a document (one possibly exported communication artifact). Two diagrams can show the same model element; editing an image independently does not necessarily update the underlying information. To gain consistency, establish identifiers and ownership. Ask: which representation is authoritative for a requirement, who changes it, and which dependent views must be regenerated?

Choose queries before notation

Begin with decisions: Can we identify all functions lacking an assigned owner? Can we find each requirement whose verification is not planned? Does changing a maximum latency invalidate a network interface design? For each question, name the model data and links needed to answer it. Only then choose the notation or tool. This prevents drawing-based MBSE theater.

A controlled model also has limits. Source observations, test results, assumptions and review judgments often originate outside the modeling tool. A governed link to an external evidence item may be more honest than copying everything into a single repository.

Worked application: follow the reasoning

Shuttle example. A new campus policy changes allowable service hours. In a document-centric workflow, an analyst searches requirements, schedules, interface notes and testing documents manually. In a model-centered workflow, requirement OPS-014 traces to operating scenario SC-02, dispatch function FN-06, timer configuration CFG-03, and tests VT-11 and VT-12. The links do not prove the change is safe; they yield a reviewable impact list that a domain expert can challenge.

Practice before viewing solutions

  1. What distinguishes a model element from a diagram symbol?
  2. Give a useful impact-analysis query for a dispatch change.
  3. When should test evidence remain external to the model?
Show worked answers
  1. What distinguishes a model element from a diagram symbol? The element has identity and semantics independent of its views. A diagram symbol is one rendering of it.
  2. Give a useful impact-analysis query for a dispatch change. Find requirements, behaviors, parts, interfaces and verification cases connected to the changed dispatch constraint; also flag absent or suspect links.
  3. When should test evidence remain external to the model? When external configuration, accreditation, raw logs or tool ownership makes a governed URI and metadata preferable to duplicating evidence.

The misconception to avoid

Watch for: Counting diagrams as evidence of integration confuses output volume with information coherence.

Applied exercise and portfolio handoff

MBSE · W02

Modeling plan, methodology, language, tool, and repository architecture

Companion chapter: EN.645.631, Week 02 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 2 for assignment, assessment criteria and complete reading plan.
Concepts: method-language-tool, modeling plan, repository schema, configuration governance
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

What must be decided before creating hundreds of model elements?

Conceptual tutorial

Separate method from syntax

A method states how a team reasons and reviews—for example, start from operational scenarios, derive functions, allocate them, and verify the resulting architecture. A language defines permitted constructs and their meaning. A tool stores, renders, queries and controls those constructs. A strong tool does not supply a sound engineering method, and a familiar diagram language does not decide who approves a change. A useful plan specifies all three independently.

Define your repository contract

Set an element naming convention, globally unique identifiers, package boundaries, owner, version, lifecycle status and required attributes before importing requirements. A simple repository can contain Need, Requirement, Behavior, Component, Interface, Constraint, TestCase and Evidence types, connected with typed relations such as derivesFrom, allocatedTo, satisfies and verifies. The information schema is the core value; a particular diagram style is a view.

Choose acceptance rules: each baselined requirement has a source and verification plan, each external interface has an owner and counterpart, and each architectural alternative is separated from the selected baseline. Require every query result to show the model revision it came from. When two people edit the same requirement concurrently, configuration controls should prevent silent overwriting.

Version-aware SysML

SysML v1 and SysML v2 differ materially in modeling concepts, syntax, tooling and interoperability. Treat the v1/v2 mapping as a conceptual translation exercise, not a guaranteed one-to-one conversion of every stereotype and diagram. Check a specific tool's support and the current official language specification.

Worked application: follow the reasoning

Repository example. A team stores REQ-37 as a single controlled element with source NEED-04, design relation to Gateway, and verification link to T-09. Two requirement diagrams reference REQ-37 without duplicating its meaning. An unreviewed change to its latency attribute marks both the downstream allocation and test case as suspect.

Practice before viewing solutions

  1. Explain why choosing a SysML editor is not choosing an MBSE methodology.
  2. Name four properties required for a controlled requirement.
  3. How should a repository represent unselected architecture alternatives?
Show worked answers
  1. Explain why choosing a SysML editor is not choosing an MBSE methodology. The editor supplies modeling operations; the method specifies analyses, decision order, review gates and acceptable evidence.
  2. Name four properties required for a controlled requirement. ID, source, owner, version/status, rationale, verification method and controlled relationships are all defensible; any four with governance are useful.
  3. How should a repository represent unselected architecture alternatives? Use separate configurations or explicit candidate status, with provenance and trade outcomes, to avoid presenting competing designs as one architecture.

The misconception to avoid

Watch for: Using tool default project structure as the engineering information architecture causes brittle models.

Applied exercise and portfolio handoff

Do: Create a modeling plan with ownership, element types, relation semantics, validation checks, and baseline procedure. Treat this as preparation for the fuller deliverables and rubric in the original Week 2 guide; the companion is not a substitute for those graded artifacts.

MBSE · W03

Stakeholders, concerns, needs, context, ConOps, and operational scenarios

Companion chapter: EN.645.631, Week 03 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 3 for assignment, assessment criteria and complete reading plan.
Concepts: stakeholder concern, operational scenario, ConOps, context model
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How do operational stories constrain what belongs in a technical model?

Conceptual tutorial

Translate voices into scenarios

Stakeholders express concerns, not always test-ready requirements. Riders may want predictable arrivals, safety staff need emergency access, and campus IT wants manageable identities. A concern becomes analyzable through an operational scenario describing actors, trigger, normal flow, abnormal variations, environment, and observable outcome. A Concept of Operations describes how the service is expected to be used, governed and sustained; it is broader than a list of features.

Construct one scene at a time. Define the system boundary and the environment. Then enumerate information or material exchanges with the dispatcher, vehicle, passenger, operator and external services. An external system is neither 'inside the model' nor 'irrelevant'—it can be outside the system-of-interest boundary while still represented as a dependency.

Scenarios reveal hidden requirements

A request to 'show ETA' seems simple until the network drops, two riders share a stop, a shuttle is taken out of service or an ETA becomes stale. Such variations reveal freshness requirements, confidence intervals, fallback messages, responsibility for status updates and operator interventions. Model each variation as a traceable branch, not as prose buried in a meeting note.

Validate the operational story with someone who performs or owns the real workflow. A technically consistent model can still represent the wrong service.

Worked application: follow the reasoning

Scenario. Trigger: passenger requests accessible pickup. Normal sequence: request → confirm boarding location → dispatch assignment → vehicle acknowledgement → passenger update. Exception: assigned vehicle becomes unavailable. The model identifies a reassignment function, a timeout, an accessible fallback and a notification responsibility. The exception exposes cross-organizational behavior absent from the happy path.

Practice before viewing solutions

  1. Why are needs and technical requirements not interchangeable?
  2. What minimum fields make a scenario reviewable?
  3. What does a network outage teach about scope?
Show worked answers
  1. Why are needs and technical requirements not interchangeable? Needs express outcomes and concerns; technical requirements allocate measurable obligations to a specific system or element.
  2. What minimum fields make a scenario reviewable? Actors, preconditions, trigger, steps, alternative flows, environment, measurable result and linked concerns.
  3. What does a network outage teach about scope? Even if the network is external, its failure behavior changes system obligations and needs an interface and fallback scenario.

The misconception to avoid

Watch for: Writing only a nominal workflow hides the conditions where interfaces become risky.

Applied exercise and portfolio handoff

Do: Author one nominal and two off-nominal scenarios, then draw context exchanges and responsible owners. Treat this as preparation for the fuller deliverables and rubric in the original Week 3 guide; the companion is not a substitute for those graded artifacts.

MBSE · W04

Requirements modeling, relationship semantics, and traceability

Companion chapter: EN.645.631, Week 04 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 4 for assignment, assessment criteria and complete reading plan.
Concepts: derivation, satisfaction, verification relation, coverage query
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

What do model links mean, beyond colored arrows?

Conceptual tutorial

Give every relation a claim

A requirement's source points toward the need or analysis that justified it. A derived requirement adds a lower-level obligation justified by design reasoning. Satisfaction asserts a design element is intended to fulfill an obligation; it does not prove compliance. Verification connects to planned procedures or results that gather evidence. Refinement makes meaning more precise in another representation. A generic trace should be used sparingly when more exact claims cannot be justified.

Relationships have cardinalities. A single operational need may yield several system requirements; one component may address multiple requirements; a requirement may need several verification cases. Preserve these many-to-many relations rather than manufacturing a single linear chain. Query for orphans, invalid targets, cycles in derivation, suspect versions and links without rationale.

Coverage is not correctness

A dashboard reporting 100% linked requirements says nothing about the quality of those links. Review a random sample bidirectionally: start from a need and locate proof of fulfillment, then start from a test and ask which requirement and risk it addresses. A link with no accountable interpretation is decoration.

When a requirement changes, do not delete its history; record previous version, reason, approval and which downstream elements require re-review.

Worked application: follow the reasoning

Trace walk. NEED-04 safe service stop → SYS-19 transition to stopped state within an illustrative 2.0 seconds → BEH-09 braking mode → CTRL-04 safety controller and IF-12 brake command → TEST-21 timed injection test. A linked test plan remains only a plan until execution evidence references the same controlled build and environment.

Practice before viewing solutions

  1. Distinguish satisfy from verify.
  2. How can 100% link coverage still be misleading?
  3. What should change-impact review include for a modified response time?
Show worked answers
  1. Distinguish satisfy from verify. Satisfy is a proposed design responsibility; verify is a relationship to evidence-gathering activities or results.
  2. How can 100% link coverage still be misleading? Links can point to unrelated elements, obsolete versions or tests with no assertions; correctness requires semantic inspection.
  3. What should change-impact review include for a modified response time? Review behavioral assumptions, component/interface allocations, units, test timing methods, environment and safety constraints.

The misconception to avoid

Watch for: Equating requirement-to-test linkage with verified compliance is an assurance error.

Applied exercise and portfolio handoff

Do: Make a 12-row trace table and write two automated orphan or stale-link queries. Treat this as preparation for the fuller deliverables and rubric in the original Week 4 guide; the companion is not a substitute for those graded artifacts.

MBSE · W05

Behavior modeling: use cases, activities/actions, interactions, states, and modes

Companion chapter: EN.645.631, Week 05 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 5 for assignment, assessment criteria and complete reading plan.
Concepts: activity, sequence interaction, state machine, mode
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

Why does one system need multiple behavioral views?

Conceptual tutorial

Different questions, different semantics

An activity model asks what actions and control flows occur. An interaction or sequence view asks which participants exchange messages and in what order. A state machine asks which states, transitions, guards and effects are legal over time. These representations overlap but are not interchangeable: a successful trip sequence does not specify what to do when a vehicle enters emergency mode during boarding.

To model behavior consistently, identify an event, precondition, guard, action/effect, postcondition and exceptional path. Use stable behavior identifiers. Distinguish a state such as AwaitingAcknowledgment from an activity such as TransmitRoute. States persist until transitions occur; actions are occurrences that consume time or produce effects.

Check cross-view consistency

If an interaction sends RouteAccepted while the state machine permits acceptance only in Ready mode, the sequence must establish that mode first. If an activity diagram has a Retry branch, identify retry limits and timeout handling in the state model. An independent review should deliberately inject an impossible event or out-of-order message and verify that the model rejects or handles it.

Behavior modeling is also an evidence design activity: each transition and high-risk scenario should eventually map to a test or demonstration.

Worked application: follow the reasoning

Dispatcher behavior. Idle → on request, SelectingVehicle → after selection, AwaitingAck → on acceptance, Assigned. If no acknowledgement arrives within 3 seconds (illustrative value), transition to Reassigning; after two failures, notify an operator. An activity view may show retry loops, but only the state machine makes legal retry counts and modes explicit.

Practice before viewing solutions

  1. Which view best establishes legal event order for a vehicle mode?
  2. How do a sequence and a state machine disagree?
  3. Why are timeout rules behavioral requirements?
Show worked answers
  1. Which view best establishes legal event order for a vehicle mode? A state machine with states, transitions, guards and effects.
  2. How do a sequence and a state machine disagree? A sequence may send a command in a state where the machine disallows it, or omit a required acknowledgement.
  3. Why are timeout rules behavioral requirements? They constrain when and how the system must respond to absence of input; they can be specified and tested.

The misconception to avoid

Watch for: Calling an action a state makes it difficult to express persistence, guards and transitions.

Applied exercise and portfolio handoff

Do: Draw a 5-state dispatcher state machine and test it against one nominal and two failed-message sequences. Treat this as preparation for the fuller deliverables and rubric in the original Week 5 guide; the companion is not a substitute for those graded artifacts.

MBSE · W06

Structure, interfaces, ports, connections, and the midcourse model review

Companion chapter: EN.645.631, Week 06 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 6 for assignment, assessment criteria and complete reading plan.
Concepts: part, port, interface contract, structural review
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How do you show that a logical connection is technically implementable?

Conceptual tutorial

Structural definitions have responsibilities

A structural model identifies system parts, their roles, composition, multiplicities and connections. An interface is a contract across a boundary; a port or equivalent boundary feature provides a place through which the interaction is exposed in a modeling language. A connection line does not yet specify protocol, message schema, units, timing, ownership or failure policy. Treat each as a separate checkable attribute.

Compare logical parts ('TripPlanner', 'RiderNotification') with physical parts (cloud service, network gateway, on-board controller). Logical functions can be reallocated; physical components incur constraints such as capacity, fault containment, weight, security zone and supply-chain responsibility. Define names in a glossary so a 'vehicle' does not alternately mean a physical platform, dispatch software proxy or operator organization.

Review structural integrity

For each external connection inspect both ends, directionality, interface version, unit consistency, timing, operating modes and provider/consumer compatibility. Detect dangling ports, multiplicity violations and unallocated behaviors. A midcourse review should challenge whether the repository can answer these questions repeatably, not reward drawing density.

Avoid treating composition as proof of physical ownership; model organizational authority and operational ownership where they differ.

Worked application: follow the reasoning

Interface audit. Vehicle telemetry port advertises speed in km/h at 2 Hz, while the dashboard consumes m/s at 1 Hz. Without an explicit converter and timestamp contract, both parts can be individually correct while the display is wrong. The model should identify transformation, stale-data handling, error bounds, accountable owner and verification procedure.

Practice before viewing solutions

  1. Can a connected pair of ports still be incompatible?
  2. What distinguishes a logical component from a deployable node?
  3. What constitutes review-ready interface evidence?
Show worked answers
  1. Can a connected pair of ports still be incompatible? Yes: a line does not ensure matching units, data schema, timing or error behavior.
  2. What distinguishes a logical component from a deployable node? A logical component groups responsibilities; a deployment node is an execution environment with physical or operational constraints.
  3. What constitutes review-ready interface evidence? Contract fields, provider/consumer mappings, negative cases, owners, configuration IDs and planned tests.

The misconception to avoid

Watch for: A visually complete internal block diagram may conceal unowned or untestable contracts.

Applied exercise and portfolio handoff

Do: Produce an interface matrix for six flows and audit one deliberately incompatible interface. Treat this as preparation for the fuller deliverables and rubric in the original Week 6 guide; the companion is not a substitute for those graded artifacts.

MBSE · W07

Logical architecture, functional allocation, derived requirements, and consistency

Companion chapter: EN.645.631, Week 07 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 7 for assignment, assessment criteria and complete reading plan.
Concepts: function allocation, logical architecture, derived requirement, consistency audit
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How do behaviors become assigned design responsibilities?

Conceptual tutorial

Allocate functions to logical owners

A functional model is not yet an architecture. To propose an architecture, map functions to logical elements and identify dependencies introduced by the split. If ComputeETA resides in the cloud and ShowETA on the vehicle, a fresh-data interface is now necessary. That interface may drive new latency and failure requirements. The architecture therefore can derive requirements, not merely satisfy an existing list.

Allocation is a design hypothesis. Compare centralized dispatch, vehicle autonomy and hybrid allocation against expected latency, safety, operations cost, resilience and configuration management. Do not use component names as a substitute for stating responsibilities. Ask what happens when a function spans multiple components: where is the orchestrating decision made and who owns failure recovery?

Check the loop

Given each critical function, verify a requirement or scenario motivates it, a logical component owns it, an interface exists for any dependency, and a test can observe its outcome. An unallocated function indicates a gap; an unexplained component may indicate gold plating. Run the checks in both directions and keep architecture alternatives distinct.

Worked application: follow the reasoning

Allocation case. ValidateEmergencyCommand is placed onboard rather than solely in central dispatch. This reduces reliance on a campus-wide network but requires authenticated local commands, local policy data, audit events and verification under link loss. Architecture allocation changes the requirements and safety argument.

Practice before viewing solutions

  1. Why can an architecture generate a new requirement?
  2. How is a function different from its owner?
  3. What does a reverse-allocation query reveal?
Show worked answers
  1. Why can an architecture generate a new requirement? The allocation introduces timing, interface, security, resource or failure dependencies absent from the initial operational statement.
  2. How is a function different from its owner? The function is behavior that must occur; its owner is a design element responsible for performing it.
  3. What does a reverse-allocation query reveal? Components with no justified functions, or duplicated responsibilities that require governance.

The misconception to avoid

Watch for: Allocating every function without recording alternatives can make one untested design look inevitable.

Applied exercise and portfolio handoff

Do: Create two allocation alternatives for five functions and compare introduced interface risks. Treat this as preparation for the fuller deliverables and rubric in the original Week 7 guide; the companion is not a substitute for those graded artifacts.

MBSE · W08

Values, units, measures, constraints, parametrics, and analysis integration

Companion chapter: EN.645.631, Week 08 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 8 for assignment, assessment criteria and complete reading plan.
Concepts: quantity kind, units, parametric constraint, sensitivity
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

What does it mean to make a system model quantitatively useful?

Conceptual tutorial

Every number needs a physical meaning

An attribute called time=4 is under-specified: is it seconds, minutes or a calendar timestamp? A well-formed quantitative model records quantity kind, unit, range, source, assumptions and revision. An analysis constraint can relate values: total response time equals sensor delay plus communication delay plus computation time plus actuator delay. The result is meaningful only if dimensions agree and any uncertain terms are treated explicitly.

A parametric relation is a calculation contract, not proof of validity. Given four delay estimates, summing their means may miss queueing interactions and high-percentile tail behavior. State whether the model is deterministic, stochastic, steady-state or transient. Choose limits that correspond to the original requirement's environment.

Trace the analysis chain

A requirement sets a threshold; design attributes and external inputs enter a constraint; the analysis produces a metric; a test or measurement tests the model's assumptions. Record provenance of numerical assumptions and perform sensitivity analysis. If the result is dominated by one poorly known term, refining other terms adds little decision value.

Worked application: follow the reasoning

Latency budget. Sensor 120 ms + network 180 ms + compute 90 ms + actuator 260 ms = 650 ms nominal. A 750 ms requirement leaves a 100 ms nominal margin. If the network could take 400 ms under congestion, the same sum becomes 870 ms and fails. A single point estimate is not a worst-case guarantee. Test with the appropriate traffic and conditions.

Practice before viewing solutions

  1. What is wrong with a bare value of 5 in a model?
  2. Compute the nominal latency margin in the example.
  3. Why does adding component mean delays not prove a tail-latency requirement?
Show worked answers
  1. What is wrong with a bare value of 5 in a model? The quantity kind, unit, source and conditions are missing.
  2. Compute the nominal latency margin in the example. 750 ms − 650 ms = 100 ms.
  3. Why does adding component mean delays not prove a tail-latency requirement? Correlation, queues, retries and distribution tails can invalidate a mean-based sum.

The misconception to avoid

Watch for: Parametric syntax cannot compensate for unverified equations or dimension errors.

Applied exercise and portfolio handoff

The question to answer

How do you compare architectures without disguising preferences as objectivity?

Conceptual tutorial

Make choices observable

A defensible trade begins with decision context, alternatives, evaluation criteria and mandatory constraints. Eliminate infeasible options before assigning soft preferences. A weighted score is a preference model, not a physical fact: criteria definitions, units, scales, weights and uncertainty must be visible. Summing scores without normalized scales can accidentally give one measure disproportionate influence.

Use at least two forms of evidence: models or calculations for quantitative constraints, and reasoned judgments with rationale for qualitative criteria. For uncertainty, run one-at-a-time sensitivity or scenarios. An alternative that wins only when an arbitrary weight is set at 0.31 rather than 0.30 is fragile. Record the break-even point and conditions under which the recommendation would change.

What the architecture review decides

The review should distinguish selected, rejected, and deferred alternatives, with consequences and assumptions. Selection is conditional on evidence: prototype results, interface contracts and verification provisions may still be outstanding. Keep the losing options accessible for future design changes; otherwise the team loses its reasoning history.

Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How do you connect model claims to evidence under a controlled build?

Conceptual tutorial

Different evidence questions

Verification asks whether the implemented system conforms to specified requirements. Validation asks whether the selected system solves real stakeholder needs in intended use. A performance test can verify a specified latency while a usability trial discovers that users cannot understand the displayed status. Neither evidence substitutes for the other.

Model a verification case with method, test configuration, input, expected result, pass threshold, boundary conditions, instrument accuracy, version and evidence location. Plan negative tests deliberately. Trace the test to the requirement, contributing design and operational scenario; attach the executed result to a controlled configuration. The plan does not itself mean the requirement has passed.

Measure meaningful coverage

Requirement coverage asks which claims have evidence. Behavior coverage asks which transitions and exceptional paths have been exercised. Architecture coverage asks whether interface contracts and allocated behaviors are checked at the appropriate integration level. A single '98% covered' number is weak unless the omitted 2% is characterized by risk. A safety-critical gap can matter more than dozens of low-risk successes.

Change control must propagate into test suites and accepted evidence; a test run from last week's firmware cannot silently verify this week's release.

Worked application: follow the reasoning

Evidence chain. OOAD · W06

Model state-dependent behavior and conduct the Analysis Model Review

Companion chapter: EN.605.704, Week 06 · Phase 1 edition 1.0 (2026-10-30)

Concepts: finite-state machine, invariant, guard, analysis review
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How do we rule out illegal behaviors over the lifetime of an object?

Conceptual tutorial

States constrain the event space

A state machine describes which states an object may occupy and which events cause transitions. For a trip: Requested, Confirmed, InProgress, Completed, Canceled. CompleteTrip from Requested is invalid. Guards are predicates evaluated before a transition, such as [vehicle acknowledged]; effects are actions performed when it occurs. Distinguish rejected events from events silently ignored by policy.

An invariant must hold in all applicable states. Examples: a completed trip has a completion timestamp; at most one active assignment exists for a trip; an active trip references a current vehicle. Invariants may span objects and require transaction design later. A state machine explains legal history; it does not make those histories safe automatically.

Conduct an analysis review

Pick scenarios from weeks 2–5 and attempt to break the models: late cancellation after boarding, lost acknowledgement, repeated assignment, data repair after power loss. Evaluate vocabulary, associations, guards, invariants and testability. Track review findings and close only with evidence. The analysis model is sufficiently mature when key domain meaning and exceptional behavior are stable enough to inform design.

Worked application: follow the reasoning

State conflict. The notification event AssignmentAccepted arrives after a trip was canceled. An unconstrained handler might revive a canceled trip. A state machine rejects the transition Canceled → Confirmed unless an explicit reinstatement use case exists; versioned commands can also prevent accepting stale acknowledgements.

Practice before viewing solutions

  1. Why is Cancel not always legal from every trip state?
  2. What distinguishes a guard from an invariant?
  3. What should an analysis-model review challenge?
Show worked answers

Companion chapter: EN.605.704, Week 10 · Phase 1 edition 1.0 (2026-10-30)
Original course: Object-Oriented Analysis and Design — find Week 10 for assignment, assessment criteria and complete reading plan.
Concepts: OCL, precondition, postcondition, change impact
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How can imprecise design claims become formal enough to challenge?

Conceptual tutorial

Precision reveals hidden choices

The Object Constraint Language (OCL) specifies invariants, preconditions and postconditions over UML models. An invariant constrains valid object states; a precondition expresses what must be true to call an operation as specified; a postcondition expresses the required result after the operation. OCL is side-effect free for logical specification; it is not ordinary execution code or a replacement for tests.

For example, context Trip inv OneActive: self.assignments->select(a | a.active)->size() <= 1 states at most one active assignment. Exact syntax depends on the model's collection types and property names; reference the OMG specification and evaluate with a compatible tool. Natural language and an executable unit test can accompany the formal expression.

Change as adversarial analysis

Introduce a new rule, such as allowing a provisional assignment while a previous assignment is closing. Now the invariant may be too strict unless 'active' is defined consistently. The redesign might alter state transitions, multiplicity, repository queries and tests. Use red-team change requests to expose unmodeled assumptions rather than to reward syntax memorization.

Worked application: follow the reasoning

Constraint exercise. Requirement: a confirmed trip has exactly one active assignment. Proposed OCL-like invariant: self.status = Confirmed implies self.assignments->select(active)->size() = 1. Test sample objects: a confirmed trip with zero active assignments violates it; a requested trip with zero does not. Decide whether a terminal trip must have zero active assignments and model separately.

Practice before viewing solutions

  1. Distinguish invariant from postcondition.
  2. Why can a correct-looking OCL expression still be wrong?
  3. What should a change red-team inspect beyond the class model?
Show worked answers
  1. Distinguish invariant from postcondition. Invariant holds for valid applicable states; postcondition describes an operation outcome.
  2. Why can a correct-looking OCL expression still be wrong? Bad vocabulary, wrong domain assumptions, inappropriate state applicability or incorrect collection semantics can invalidate intent.
  3. What should a change red-team inspect beyond the class model? State machines, interactions, persistence, APIs, requirements, tests and migration assumptions.

The misconception to avoid

Watch for: Formal syntax without domain validation gives precise but false assertions.

The underlying problem: different pictures of one thing

A model is a claim about the world, not just a visual aid. If a requirement is displayed in three diagrams, those three shapes should not become three independent requirements. Identity is the key: an element needs a stable ID, a type, attributes, status and provenance, then views can render it according to a stakeholder's concern. The sophistication of a drawing tool matters less than whether the data remains consistent when you change it.

Suppose REQ-S-12 describes reporting dispatch status. A model may connect it to NEED-R-02, function FN-REPORT, software component SVC-NOTIFY and test T-FRESH. Each relation makes a different claim. derivedFrom says a source justifies an obligation, allocatedTo says someone must realize behavior, and verifiedBy says a procedure supplies evidence about conformance. Do not use one generic 'links-to' relation when the review question requires a precise claim.

A small relational model

Start with two data structures:

Element(id, kind, title, revision, owner, status, source)
Link(source_id, relation_type, target_id, rationale, review_status)

Constraints then become possible: every link endpoint exists; IDs are unique; every baselined requirement has at least one source; every high-consequence requirement has a planned verification; an allocation targets a function or component of a permissible type; and every changed target generates an impact queue. These checks are necessary, but still not sufficient. 'All requirements have a source' can be satisfied by connecting everything to an irrelevant stakeholder need. Semantic quality requires review of samples and high-risk paths.

Query design and review

Write the engineering question first. 'What changed?' needs revision comparisons. 'Are we ready to test?' needs requirements-to-test paths and test status. 'If the gateway is removed, what depends on it?' needs both direct and transitive impact queries. Keep model quality separate from V&V completion: a model may be internally consistent while representing incorrect physics or operations. Record both automated-rule reports and reviewed claims.

Operational scenarios, use cases and software responsibilities

Concept library essay · Phase 1

One mission, three different abstractions

An operational scenario answers what people and the system must accomplish in context. A software use case answers how a user goal interacts with the software boundary. A software architecture design answers where responsibilities live and what interfaces realize the use case. These descriptions overlap but their boundaries differ. If an autonomous vehicle enters a safe state when a communications link fails, the operational scenario may describe the full service consequence; the software use case may only describe a dispatcher alert; the onboard controller's logic may be outside the software team's authority.

Take 'rider requests pickup.' The operational scenario includes physical accessibility, stop selection, weather, fleet readiness and fallback transport. The software use case focuses on entering a request, eligibility validation, finding capacity, confirmation and failure. The design introduces policies, transactions, APIs and storage. Treating the design as the use case hides which choices are contingent and which user outcomes are obligatory.

Deriving software requirements from a narrative

Use the following pipeline: (1) identify actors and outcomes; (2) identify each actor/system interaction; (3) enumerate normal, exceptional and malicious variations; (4) establish software versus nonsoftware authority; (5) specify measurable requirements; (6) connect candidate domain concepts; (7) map to verification or validation ideas. Example: a rider expects confirmation. Instead of 'the platform shall confirm immediately', write an illustrative measurable receipt requirement with workload and percentile, a separate booking-state requirement and a separate degraded-mode notification policy.

Avoid accidental safety claims

The most dangerous ambiguity is confusing 'command acknowledged' with 'action accomplished.' A platform API may return HTTP 200 after a message is queued; that does not establish that a vehicle has executed it. Define event stages: accepted, enqueued, delivered, onboard validated, executed, observed. Different stages require different sensors and authorities. A graph of these stages is a more useful safety artifact than an optimistic status flag.

What remains the same

Across SysML generations, engineers still need to express requirements, parts, behavior, quantitative constraints and relationships to analyses and evidence. A stakeholder does not care which syntax encodes a latency requirement; they care whether it is unambiguous, consistently allocated and defensible by test evidence. For the same shuttle example, represent five concepts without committing to notation: (1) need for predictable arrivals; (2) requirement for status freshness; (3) function to publish updates; (4) part or service responsible for publishing; (5) verification case under network disruption. Use a capability checklist to test whether your tool can query links, version models, export interoperably and validate constraints.

Export a small, reviewed baseline from a v1 tool if you have one. Import or recreate a controlled subset in a v2 implementation. Report unsupported semantics instead of silently omitting them. Preserving a JPEG image does not preserve a model.

The OMG SysML 2.0 language specification, formally adopted in 2025 and published with editorial updates in 2026, should be your normative reference. Vendor tutorials may be useful for a tool but do not override specification semantics.

State machines, invariants and precise behavioral contracts

Concept library essay · Phase 1

Why state matters more than method names

A request may be valid in one state and forbidden in another. A model that exposes cancelTrip() without a state contract cannot tell you whether cancellation is allowed after boarding, during a pending assignment or after completion. State models make this visible. A transition consists of source state, triggering event, optional guard, effect and target state. An event that arrives outside its permitted state requires an explicit disposition, not a vague promise to 'handle errors'.

Represent a small trip lifecycle:

Requested --confirm--> Confirmed --board--> InProgress --finish--> Completed
    |                    |
  cancel               cancel (under policy)
    v                    v
 Canceled             Canceled

An invariant might be: at most one assignment is active for a trip. The state machine alone does not guarantee this across concurrent database transactions. A precise contract requires both model-level assertion and implementation-level enforcement. This illustrates the different roles of UML/OCL, test cases, and database constraints.

Think with counterexamples

Take the claim 'every confirmed trip has an active vehicle.' Construct objects that challenge it: confirmed trip with zero assignments, two active assignments, assignment to an unavailable vehicle, or an assignment that expired one microsecond ago. Is the claim supposed to hold before or after a transaction completes? If a system is eventually consistent, which authoritative component enforces it? Do not allow ambiguity over time windows to hide in natural language.

Connect model and executable tests

For each transition write a positive test, a rejected-event test and one cross-object invariant test. Add stale-message and duplicate-message variants. An operation's precondition tells callers when a command is meaningful; its postcondition describes what the command guarantees if it succeeds. Tests should also check that a rejected command leaves persistent state unchanged unless audit requirements explicitly demand a side effect.

DEEP DIVE · CONCEPT LIBRARY

Distributed systems: timeouts, duplicates and eventual knowledge

Concept library essay · Phase 1

The uncertainty behind a timeout

A caller sends a command to another process. The remote process updates its database but crashes before returning success. The caller observes a timeout. Was the command executed? Yes. Can the caller know from the timeout? No. Retrying can cause a second side effect unless the operation is idempotent. This is not an edge case caused by sloppy code; it follows from unreliable communication between independent failure domains.

A practical idempotency design stores a token, a canonical request representation, the resulting decision and the associated transaction. A second request with the same token and payload returns the same decision; the same token with a different payload is rejected. This can prevent duplicate effects for the protected operation. You still need to handle token retention, expired tokens, data migration and the difference between server state and external side effects.

Consistency is a product decision

A dispatcher cannot assign the same unique accessible vehicle twice to overlapping trips. This invariant probably belongs within one authoritative transactional boundary. Rider status displays can be eventually consistent, as long as the user interface explains staleness and no safety decision relies solely on that stale projection. Strong coordination and availability under network partition pull in different directions: the correct answer depends on the business invariant and failure consequences.

Compensating actions

A distributed workflow may not be able to atomically update a reservation database and a third-party notification provider. A transactional outbox records business change plus pending outbound event in one local transaction. A relay publishes later, potentially more than once; consumers deduplicate by event ID. If an external booking was created and a later step fails, a cancellation/compensation may be needed. Such compensation is a business action, not magic rollback of time.

Practice

Simulate lost acknowledgement after a successful reservation. Show the database before and after retry. Then add a duplicate event and an out-of-order cancellation. Define what the client may safely display at each point. tools/reservation_service.py provides an executable toy model, not a production distributed transaction manager.

DEEP DIVE · CONCEPT LIBRARY

Quantitative performance and reliability without misleading averages

Concept library essay · Phase 1

From a headline metric to a measurable hypothesis

Latency requirements need trigger, endpoints, workload, environment, statistic and threshold. A 500 ms average and a 500 ms 99th percentile describe different performance distributions. If 1% of requests take 20 seconds, an average can remain seemingly reasonable while users experience serious delays. Always inspect a histogram or percentile table and document how load and failures were generated.

An end-to-end budget is useful for reasoning, even before code. Suppose a rider update has contributions of 80 ms ingress, 150 ms queuing, 120 ms processing, 100 ms persistence and 200 ms egress. The 650 ms sum leaves 250 ms under a 900 ms nominal target. But queuing is load-sensitive, and independent percentile budgets cannot simply be added to prove an end-to-end percentile without statistical assumptions. Measure the composed system.

Queueing intuition

Little's Law relates average in-system work, arrival rate and average time: L = λW for a stable system over an appropriate observation period. If a service receives 25 requests per second and average total response time is 0.4 seconds, expected average concurrent requests in the system is 10. This does not imply every burst is safe. A bottleneck approaching saturation can have rapidly rising queues even when mean service duration changes little.

Reliability accounting

A nominal monthly 99.9% availability target gives 0.1% downtime budget. At 30 days, 0.001 × 43,200 minutes = 43.2 minutes. However, actual SLA formulas may exclude maintenance, distinguish partial errors, or use request-based success rather than clock availability. Expose the denominator and measurement rules. Series availability of independent components can multiply component probabilities; common-cause failures and dependent infrastructure invalidate naïve independence assumptions.

Uncertainty and decisions

Use an experiment ledger: hypothesis, fixed conditions, varied factors, observed samples, confidence/limitations and release implication. A load test of 1,000 synthetic calls in a lab does not establish field availability over a month. Favor explicit limitations over false precision. tools/performance_budget.py calculates basic budgets and illustrates what the math can and cannot claim.

Change impact, provenance and controlled evidence

Concept library essay · Phase 1

One change touches several models

Change the status freshness requirement from 10 seconds to 3 seconds. At first it looks like editing one threshold. But the system behavior may need a faster event cycle; the interface must preserve timestamps; cloud budgets and mobile push behavior may change; stale-state policy may become more visible; old tests no longer establish compliance. The correct unit of change analysis is a set of claims and dependencies, not the paragraph that carried the original number.

Track every element with a stable ID and revision. A dependency link should have a declared meaning and version relevance. When REQ-ETA changes, traverse to functions and designs, then to analysis inputs and tests; label links as confirmed, suspected or explicitly unaffected after review. Preserve older baselines so historical test runs remain interpretable.

A minimum change workflow

  1. Record change request, source, reason, proposed target and impact window.
  2. Query direct and transitive dependencies; expand scope through domain-expert review.
  3. Identify decisions, tests, data models and operating procedures with likely impact.
  4. Propose alternatives and evaluate cost, risk and risk of not changing.
  5. Approve an implementation baseline and assign work.
  6. Update models and evidence, rerun checks and publish new controlled state.

A change report should explain why a linked element is or is not affected. A generated list of 400 links without prioritization is not useful decision support. Focus on high-consequence chains first.

Practice

Use the model_graph.py tool to find transitive impact of a changed requirement. Compare its mechanically inferred set to a human-reviewed set. Mark at least one false positive and one missing link. This teaches why automated traces accelerate—not replace—systems reasoning.

DEEP DIVE · CONCEPT LIBRARY

Security, safety and release evidence as structured claims

Concept library essay · Phase 1

Assurance starts with a bounded claim

A claim like 'the platform is safe and secure' is too broad to establish. Instead say 'the assignment service prevents duplicate active assignments in the specified simulated concurrency workload' and link the claim to design controls, tests, versions and conditions. A nested argument can show why a system-level claim depends on software, physical components, operating procedure and organizational response. Explicit assumptions are essential.

Security threats involve adversarial intent; accidental failures involve faults and mistakes; both may trigger similar controls. An API request can be authenticated but unauthorized. An event message can be well-formed but semantically stale. A supply-chain dependency can be unmodified in your source tree yet compromised upstream. Threat modeling identifies assets, entry points, trust boundaries and attack narratives. A failure mode review identifies component faults, effects, detection and recovery. Neither activity alone proves controls work.

Evidence has quality levels

A design review can show a mitigation is intended. A unit test can show one local rule works. An integration test can show a particular interface behavior. A representative operational test can show a specified system behavior in one environment. Long-run field measurements and independent assessments answer different questions. Good assurance arguments attach the right level of evidence to the right claim.

A release review under uncertainty

Assemble a table with claim, requirement ID, criticality, supporting evidence, configuration, outstanding gap, consequence and disposition. Define mandatory go/no-go rules before seeing favorable test results; otherwise the team may move the threshold to fit the evidence. Approval should be scoped: the lab simulator may be ready while the public-road system is not. Keep residual risks visible and owned.

Practice

Create an assurance claim for duplicate assignment prevention, then deliberately inject three counterexamples: concurrent writes, replay after timeout and manual database repair. Which tests and operational controls are needed? Reference NIST SSDF for secure development practices and your original course guide for release rubric.
