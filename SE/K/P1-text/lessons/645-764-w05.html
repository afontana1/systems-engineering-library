Integrate agile product engineering with systems evidence

Companion chapter: EN.645.764, Week 05 · Phase 1 edition 1.0 (2026-10-30)
Original course: Software Systems Engineering — find Week 5 for assignment, assessment criteria and complete reading plan.
Concepts: agile increment, trace evidence, definition of done, feedback
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How do iterative delivery and systems assurance reinforce each other?

Conceptual tutorial

Iteration is not evidence avoidance

Agile increments reduce uncertainty by delivering thin, usable slices and collecting feedback. Systems engineering reduces uncertainty by maintaining traceability, interface coherence, hazards and verification. These are compatible if the definition of done includes appropriate tests, reviewed requirements, interface versions and evidence for the increment's risk. A sprint review cannot substitute for release assurance.

Slice by end-to-end behavior rather than subsystem-only activity when practical. An early vertical slice may cover request → assignment → rider confirmation with an in-memory vehicle catalog, while explicitly excluding road deployment. Record which system requirements are satisfied, which tests run and which interface assumptions remain. Avoid pretending a prototype meets production availability or security standards.

Separate product velocity from assurance progress

Velocity measures throughput of planned work; it does not establish reduction of critical risks. Track leading indicators such as time to resolve interface defects, proportion of high-risk scenarios tested, deployment rollback success and evidence age. A backlog item can carry model-link IDs and closure criteria.

Worked application: follow the reasoning

Vertical slice. Sprint 1 implements an offline simulation of an assignment request, one allocation policy, unit tests and an interface contract stub. Sprint 2 adds event persistence and duplicate-message handling. At both milestones a trace report identifies unverified field-deployment requirements; progress is real but bounded.

Practice before viewing solutions

  1. What does a risk-aware definition of done include?
  2. Why is sprint velocity not an assurance metric?
  3. What distinguishes a prototype from a release candidate?

<details> <summary><strong>Show worked answers</strong></summary>

  1. What does a risk-aware definition of done include? Acceptance behavior, required tests, security/interface checks, trace links, review disposition and artifacts appropriate to risk.
  2. Why is sprint velocity not an assurance metric? It measures work throughput, not severity of unresolved hazards or fidelity of evidence.
  3. What distinguishes a prototype from a release candidate? Production-quality obligations, operating conditions, controlled configuration and release evidence remain to be satisfied.

</details>

The misconception to avoid

Watch for: Calling all incomplete assurance activities “technical debt” can obscure mandatory release gates.

Applied exercise and portfolio handoff

Do: Plan three vertical increments with explicit evidence, assumptions and release-exclusion labels. Treat this as preparation for the fuller deliverables and rubric in the original Week 5 guide; the companion is not a substitute for those graded artifacts.
