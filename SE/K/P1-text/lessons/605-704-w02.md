# Elicit and structure software requirements

**Companion chapter:** EN.605.704, Week 02 · Phase 1 edition 1.0 (2026-10-30)  
**Original course:** [Object-Oriented Analysis and Design](../../../C/P1/EN605704.md) — find **Week 2** for assignment, assessment criteria and complete reading plan.  
**Concepts:** elicitation, functional requirement, quality scenario, ambiguity  
**Use of case:** Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

## The question to answer
> How can stakeholder conversation produce software obligations that can actually be checked?

## Conceptual tutorial

### Observe work, not only wishes
Interviewing stakeholders is insufficient if the analyst never studies the actual workflow, exceptions, logs and terminology. Compare perspectives: riders describe pickup, dispatchers describe capacity, accessibility staff describe equitable service, operators describe fallback procedures. Record conflicts explicitly. A claim of 'fast assignment' becomes meaningful only after defining trigger, load, environment, statistic and threshold.

Classify functional requirements as observable system behaviors and nonfunctional requirements as measurable qualities or constraints (latency, availability, audit retention, access control). Qualities often cross use cases; specify them using a stimulus–environment–response–measure structure. Distinguish what the software controls from an external outcome it can influence but not guarantee.

### Make requirements test-seeking
Avoid words such as 'robust', 'intuitive' and 'secure' without measures. Replace 'the app must be fast' with a bounded statement such as 'For 95% of valid requests at 100 concurrent users in the test workload, return an initial receipt within 500 ms.' Even that needs agreed workload and measurement instrumentation. Write an exception path for failures. Trace each requirement to a source scenario and planned evidence.

## Worked application: follow the reasoning

**Shuttle case.** A dispatcher asks for 'immediate cancel.' Interview reveals two meanings: prevent future assignment and stop an already moving shuttle. The first is platform responsibility; the second belongs to an onboard safety-authorized procedure. Conflating them in a single software requirement would create an unsafe expectation.

## Practice before viewing solutions

1. What fields make a performance requirement testable?
2. Why is a cancellation requirement ambiguous?
3. Distinguish a requirement from an architecture decision.

<details>
<summary><strong>Show worked answers</strong></summary>

1. **What fields make a performance requirement testable?** Trigger, workload, environment, response, statistic/threshold and measurement method.
2. **Why is a cancellation requirement ambiguous?** Cancel might mean retract a request, withdraw assignment, notify rider or command vehicle motion; specify authority and state.
3. **Distinguish a requirement from an architecture decision.** Requirement states observable obligation and constraints; decision selects how software will realize it.

</details>

## The misconception to avoid

**Watch for:** A requirements table can look complete while hiding conflicting stakeholder definitions.
