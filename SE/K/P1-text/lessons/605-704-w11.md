## The question to answer
> How should a design survive storage, transactions and evolving schemas?

## Conceptual tutorial

### Persistence changes the design problem
A domain class is not a table, and an association is not always a foreign key. Persistence must preserve identity, lifecycle, invariants, concurrency and reporting needs. Choose which concepts are aggregates with transactional consistency boundaries. Normalize where independent facts must not conflict; denormalize only when measurable access patterns justify maintenance cost.

Map a domain `Trip` to storage that can answer current and historical assignment questions. A row holding only `current_vehicle_id` loses reassignment provenance; an assignment-history table may be required. Time-related rules need precise timestamps and time zones. An optimistic concurrency version prevents blind overwrite when two dispatchers update the same trip.

### Review for evolution
A schema migration is not a rename in a diagram. Consider historical records, mixed software versions, rollback, privacy retention, access controls and repair scripts. A design-readiness review must demonstrate that failure during migration or deployment does not violate core business guarantees. Keep repository interfaces defined by domain needs, not every ad hoc query in the ORM.

## Worked application: follow the reasoning

**Schema choice.** `trip(id, status, version)` and `assignment(id, trip_id, vehicle_id, active, valid_from, valid_to)` support history. A transaction updates prior active assignment to false and inserts the new one while enforcing no more than one active per trip. Exact DB constraints depend on the selected platform.

## Practice before viewing solutions

1. Why might a direct class-to-table mapping be insufficient?
2. What does a version field support?
3. What should the design review demand of a migration plan?

<details>
<summary><strong>Show worked answers</strong></summary>

1. **Why might a direct class-to-table mapping be insufficient?** Historical relationships, transactions, polymorphism and value objects may require different schema structures.
2. **What does a version field support?** Optimistic concurrency: reject updates based on stale state rather than silently overwriting.
3. **What should the design review demand of a migration plan?** Backfill and rollback strategy, mixed-version compatibility, data integrity and security evidence.

</details>

## The misconception to avoid

**Watch for:** Assuming an ORM enforces every domain invariant leads to race conditions and lost history.
