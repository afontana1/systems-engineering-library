# Interpret and critique the system model for software realization

**Companion chapter:** EN.645.764, Week 03 · Phase 1 edition 1.0 (2026-10-30)  
**Original course:** [Software Systems Engineering](../../../C/P1/EN645764.md) — find **Week 3** for assignment, assessment criteria and complete reading plan.  
**Concepts:** model critique, assumption, gap analysis, technical risk  
**Use of case:** Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

## The question to answer
> How should software engineers challenge, rather than inherit, a system model?

## Conceptual tutorial

### Read a model skeptically
Models often appear authoritative because they are precise. Before implementing allocated functions, test assumptions against deployment reality: networks partition, clocks drift, messages duplicate, systems reboot and human operators override automation. Check whether the model specifies resources, ordering, modes, negative cases and recovery actions.

Use a structured critique: (1) completeness, (2) consistency, (3) realizability, (4) observability, (5) risk. A system requirement for 'instant status' may be unrealizable without bounding distance, load and outage behavior. An activity model can omit concurrency. A requirements trace may hide a test-only assumption about stable connectivity. Record findings as controlled issues tied to model element IDs.

### Turn critique into action
For each model issue, propose one of: clarify requirement, add constraint, change allocation, create analysis experiment, change interface contract or accept a documented risk with authority. Reject 'just code a workaround' unless the system owner agrees to the resulting semantics. Translate findings into software experiments early.

## Worked application: follow the reasoning

**Critique.** A dispatcher model assumes every assignment acknowledgement arrives within 500 ms. At a remote stop, network telemetry shows occasional 3-second delay. The implementation must either expose a longer deadline, use provisional state and reconciliation, or change the physical communications architecture. Hiding the issue with retries alone creates duplicate-assignment risk.

## Practice before viewing solutions

1. What four physical-world issues can invalidate a system model?
2. What is a legitimate disposition for an unresolved assumption?
3. Why should model critique precede code?

<details>
<summary><strong>Show worked answers</strong></summary>

1. **What four physical-world issues can invalidate a system model?** Partitions, clock drift, duplicate/out-of-order messages, resource limits, reboot or operator action; any four.
2. **What is a legitimate disposition for an unresolved assumption?** Evidence-gathering experiment, allocated fix, requirement clarification or authorized risk acceptance with tracking.
3. **Why should model critique precede code?** Implementation may bake false assumptions into interfaces and persistent data structures.

</details>

## The misconception to avoid

**Watch for:** Assuming upstream models are unquestionably correct transfers uncertainty into costly implementation.
