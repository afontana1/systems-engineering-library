## The question to answer
> What must a software model decide before class diagrams appear?

## Conceptual tutorial

### Discover the domain before designing the code
Analysis models describe the problem: passengers, trips, assignments, cancellations, operating policies and exceptional cases. Design models describe the proposed software solution: services, controllers, repositories, message handlers and persistence. Mixing them too early causes technology choices to masquerade as domain truths. A `Trip` can belong to domain analysis; `TripSqlRepository` does not.

Separate four types of statements: stakeholder concern ('I need reliable pickup'), domain rule ('an active trip has one assigned vehicle'), software obligation ('confirm requests within 2 seconds under stated load'), and design choice ('use an event queue'). Each should have a source and validation method. UML provides different diagram families for structure, interaction, activity and state. The question decides the view: class diagrams are poor at ordering asynchronous events; sequence diagrams are poor at defining stable cardinalities.

### Scope is a deliberate constraint
The software platform coordinates dispatch and customer updates; it need not implement vehicle motion control. Mark external actors and systems honestly. Clarify what happens if an external service fails. Identify the vocabulary and the first three use cases before adopting a framework.

## Worked application: follow the reasoning

**Model boundary.** Rider requests a trip; platform assigns a vehicle and reports status. An external onboard controller retains authority over safe motion. The software design cannot assume dispatch acknowledgements equal safe vehicle behavior. In the initial domain glossary, `TripRequest` and `VehicleAssignment` are separate because requests can be rejected or reassigned.

1. **Classify `Trip`, `TripController`, and `SQLTripRecord`.** Trip is a domain concept, TripController a software design element, and SQLTripRecord a persistence representation.
2. **Why is a class diagram insufficient for a timeout?** Timeout requires time, events, state and behavior that class structure alone does not express.
3. **Give a domain rule separate from an implementation choice.** Rule: each active assignment references one available vehicle. Choice: enforce it in an application service and database transaction.

## The misconception to avoid

**Watch for:** Treating an implementation architecture as discovered domain truth biases every later analysis artifact.
