## The question to answer
> How do you maintain traceability when multiple engineering models disagree?

## Conceptual tutorial

### Connect models without pretending they are identical
An MBSE behavior can allocate to a software service, an OOAD operation may realize a subset of that behavior, an API contract exposes an interaction, and a test verifies an observable requirement. These are distinct element types with different abstraction levels. A digital thread records their typed relationships and revisions so changes can be assessed across tool boundaries.

Define relationship semantics. `allocatedTo` names responsibility, `realizedBy` connects intent to implementation, `testedBy` names evidence procedure, and `observedIn` identifies executed results. For every cross-tool link store target ID, authoritative source, version, link rationale and validation time. Query for missing owners, incompatible versions, unverified critical requirements and duplicate interface definitions.

### Interfaces are active risks
An API schema describes structure; a full interface contract also states timing, access control, retry policy, failure semantics, units and configuration negotiation. It needs a consumer perspective. A compatible JSON schema does not ensure that two services interpret a field the same way. Include semantic examples and negative tests.

## Worked application: follow the reasoning

**Trace chain.** `SYS-Need: accurate rider status` → `SYS-FN: publish updates` → `SW-SVC: NotificationService` → `API-05: trip-status/v2` → `IT-12: stale event rejection` → `RUN-65: passed on build B`. Each link is directed, typed and versioned; a schema v3 change marks related tests and consumers for review.

## Practice before viewing solutions

1. Why should link types have different meanings?
2. What belongs in an interface contract beyond schema?
3. How can a digital thread be present but untrustworthy?

<details>
<summary><strong>Show worked answers</strong></summary>

1. **Why should link types have different meanings?** Allocation, implementation and verification are different engineering claims and require different evidence.
2. **What belongs in an interface contract beyond schema?** Timing, units, authorization, idempotency, failures, version compatibility and owner.
3. **How can a digital thread be present but untrustworthy?** Broken/stale links, missing provenance, mismatched versions or purely syntactic relationships without semantic validation.

</details>

## The misconception to avoid

**Watch for:** An ungoverned hyperlink collection is not an auditable digital thread.
