# Values, units, measures, constraints, parametrics, and analysis integration

## The question to answer
> What does it mean to make a system model quantitatively useful?

## Conceptual tutorial

### Every number needs a physical meaning
An attribute called `time=4` is under-specified: is it seconds, minutes or a calendar timestamp? A well-formed quantitative model records quantity kind, unit, range, source, assumptions and revision. An analysis constraint can relate values: total response time equals sensor delay plus communication delay plus computation time plus actuator delay. The result is meaningful only if dimensions agree and any uncertain terms are treated explicitly.

A parametric relation is a **calculation contract**, not proof of validity. Given four delay estimates, summing their means may miss queueing interactions and high-percentile tail behavior. State whether the model is deterministic, stochastic, steady-state or transient. Choose limits that correspond to the original requirement's environment.

### Trace the analysis chain
A requirement sets a threshold; design attributes and external inputs enter a constraint; the analysis produces a metric; a test or measurement tests the model's assumptions. Record provenance of numerical assumptions and perform sensitivity analysis. If the result is dominated by one poorly known term, refining other terms adds little decision value.

## Worked application: follow the reasoning

**Latency budget.** Sensor 120 ms + network 180 ms + compute 90 ms + actuator 260 ms = 650 ms nominal. A 750 ms requirement leaves a 100 ms nominal margin. If the network could take 400 ms under congestion, the same sum becomes 870 ms and fails. A single point estimate is not a worst-case guarantee. Test with the appropriate traffic and conditions.

## The misconception to avoid

**Watch for:** Parametric syntax cannot compensate for unverified equations or dimension errors.
