The question to answer

How can imprecise design claims become formal enough to challenge?

Conceptual tutorial

Precision reveals hidden choices

The Object Constraint Language (OCL) specifies invariants, preconditions and postconditions over UML models. An invariant constrains valid object states; a precondition expresses what must be true to call an operation as specified; a postcondition expresses the required result after the operation. OCL is side-effect free for logical specification; it is not ordinary execution code or a replacement for tests.

For example, context Trip inv OneActive: self.assignments->select(a | a.active)->size() <= 1 states at most one active assignment. Exact syntax depends on the model's collection types and property names; reference the OMG specification and evaluate with a compatible tool. Natural language and an executable unit test can accompany the formal expression.

Change as adversarial analysis

Introduce a new rule, such as allowing a provisional assignment while a previous assignment is closing. Now the invariant may be too strict unless 'active' is defined consistently. The redesign might alter state transitions, multiplicity, repository queries and tests. Use red-team change requests to expose unmodeled assumptions rather than to reward syntax memorization.

Worked application: follow the reasoning

Constraint exercise. Requirement: a confirmed trip has exactly one active assignment. Proposed OCL-like invariant: self.status = Confirmed implies self.assignments->select(active)->size() = 1. Test sample objects: a confirmed trip with zero active assignments violates it; a requested trip with zero does not. Decide whether a terminal trip must have zero active assignments and model separately.

Practice before viewing solutions

  1. Distinguish invariant from postcondition.
  2. Why can a correct-looking OCL expression still be wrong?
  3. What should a change red-team inspect beyond the class model?

<details> <summary><strong>Show worked answers</strong></summary>

  1. Distinguish invariant from postcondition. Invariant holds for valid applicable states; postcondition describes an operation outcome.
  2. Why can a correct-looking OCL expression still be wrong? Bad vocabulary, wrong domain assumptions, inappropriate state applicability or incorrect collection semantics can invalidate intent.
  3. What should a change red-team inspect beyond the class model? State machines, interactions, persistence, APIs, requirements, tests and migration assumptions.

The misconception to avoid

Watch for: Formal syntax without domain validation gives precise but false assertions.
