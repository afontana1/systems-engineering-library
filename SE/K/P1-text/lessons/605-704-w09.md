# Apply design patterns with restraint

**Companion chapter:** EN.605.704, Week 09 · Phase 1 edition 1.0 (2026-10-30)  
**Original course:** [Object-Oriented Analysis and Design](../../../C/P1/EN605704.md) — find **Week 9** for assignment, assessment criteria and complete reading plan.  
**Concepts:** strategy, observer, adapter, pattern tradeoff  
**Use of case:** Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

## The question to answer
> When does a design pattern solve a real change problem?

## Conceptual tutorial

### Patterns are explanations for recurring forces
A **Strategy** isolates interchangeable policies behind a stable contract, such as vehicle-selection algorithms. An **Adapter** translates between an external provider's representation and your domain interface. An **Observer** or event-driven publish/subscribe arrangement distributes state-change notifications. Each pattern introduces complexity, so name the variability or coupling it addresses before applying it.

Patterns are not proof of good architecture. A Strategy with one unlikely-to-change algorithm may add indirection for no benefit. An Observer can create ordering and duplicate-delivery challenges. A Singleton can introduce hidden mutable global state and testing difficulty. Favor the simplest solution that satisfies a visible change or quality scenario.

### Evaluate alternatives explicitly
For each candidate pattern describe the current pain point, expected variation, responsibilities before and after, effect on testability and failure modes. Patterns combine: an adapter at the external messaging boundary and a strategy for selection policy can be useful without infecting every class with factories and interfaces.

## Worked application: follow the reasoning

**Dispatch strategy.** Policy A selects the nearest available vehicle; policy B prioritizes accessibility and battery reserve. Both implement `select(request, candidates) -> decision`. Separate policy tests show different results for the same synthetic inputs. A runtime configuration controls activation with an audit trail. The design is justified if policy change is likely and behavior differs enough to matter.

## Practice before viewing solutions

1. When does Strategy earn its complexity?
2. What cost can Observer introduce?
3. What does an Adapter protect?

<details>
<summary><strong>Show worked answers</strong></summary>

1. **When does Strategy earn its complexity?** When rules vary independently and need isolated tests or controlled selection.
2. **What cost can Observer introduce?** Ordering, duplicate events, lost delivery, debugging and eventual-consistency complexity.
3. **What does an Adapter protect?** The domain model from external schemas, API changes and vendor-specific data structures.

</details>

## The misconception to avoid

**Watch for:** Pattern catalogs are not checklists; indiscriminate patterns obscure responsibilities.

## Applied exercise and portfolio handoff

**Do:** For two anticipated changes, choose a pattern or no pattern and compare consequences. Treat this as preparation for the fuller deliverables and rubric in the original **Week 9** guide; the companion is not a substitute for those graded artifacts.
