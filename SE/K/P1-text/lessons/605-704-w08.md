# Realize use cases with dynamic design models

**Companion chapter:** EN.605.704, Week 08 · Phase 1 edition 1.0 (2026-10-30)  
**Original course:** [Object-Oriented Analysis and Design](../../../C/P1/EN605704.md) — find **Week 8** for assignment, assessment criteria and complete reading plan.  
**Concepts:** dynamic design, transaction boundary, concurrency, error handling  
**Use of case:** Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

## The question to answer
> What extra behavior appears when analysis collaborations must actually execute?

## Conceptual tutorial

### Design realizes a use case under technical constraints
An analysis interaction says 'reserve vehicle'; design must specify who begins and commits the transaction, how concurrent requests are handled, what happens after a partial failure, and how the caller learns the outcome. Define interface signatures with inputs, outputs, errors and idempotency keys. Show both success and failure messages. Avoid assuming that a remote call is atomic with a local database write.

A distributed workflow may need a **compensating action** rather than rollback. For example, after saving an assignment but before notifying the rider, a message may fail. Persist an event to an outbox in the same transaction, then deliver it asynchronously and tolerate duplicates. The notification result is not the same as the reservation state.

### Sequence models should expose operational conditions
Annotate concurrency, lock or optimistic-version policy, timeout ownership, retries and observability. Test a conflicting request against the same resource. The goal is not diagram complexity but a defensible realization of the use-case guarantees.

## Worked application: follow the reasoning

**Concurrent reservation.** Two riders request the final accessible vehicle. Both can read the same candidate list. A database uniqueness/locking strategy ensures only one active reservation wins; the losing transaction retries selection or returns a capacity outcome. A screen-level check before saving is insufficient because the race occurs later.

## Practice before viewing solutions

1. Why does a successful read not guarantee a reservation?
2. What is the outbox pattern trying to prevent?
3. How does an application sequence improve on an analysis sequence?

<details>
<summary><strong>Show worked answers</strong></summary>

1. **Why does a successful read not guarantee a reservation?** Another request can act between read and write; atomicity or version controls protect the invariant.
2. **What is the outbox pattern trying to prevent?** A committed business state without a reliably deliverable event when database and broker commits cannot share a transaction.
3. **How does an application sequence improve on an analysis sequence?** It specifies real interfaces, transactional boundaries, failures, concurrency and technical responsibilities.

</details>

## The misconception to avoid

**Watch for:** Using the network as if it supported one global transaction is a major design misconception.
