Integrated model baseline, capstone review, oral defense, and lessons learned

Companion chapter: EN.645.631, Week 12 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 12 for assignment, assessment criteria and complete reading plan.
Concepts: integrated baseline, assurance argument, technical defense, portfolio evidence
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

What proves a system model is useful enough for a real design review?

Conceptual tutorial

Build a decision narrative, not a diagram gallery

A capstone model should connect mission concerns to requirements, behavior, architecture, quantitative constraints, interface obligations, candidate selection and V&V. A reviewer should be able to follow any consequential claim backward to its source and forward to evidence or a controlled open issue. Show a repeatable query demonstration—not just a set of static screenshots.

A technical defense should walk three difficult threads: a normal mission scenario, a credible fault scenario, and a requirements change. For each, locate the relevant model elements and state uncertainty. The best model review also admits what it cannot answer, which assumptions are least mature and which decisions remain conditional.

Prevent false closure

Do not infer that a model makes the real shuttle safe or complete. The model supports engineering decisions; actual release requires implementation, physical testing, independent review and operating authority. A credible course-exit package contains revisioned model export, schema, crosswalk, executable checks, query results, trade rationale, outstanding risk and lessons learned.

Worked application: follow the reasoning

Review demonstration. A sponsor changes maximum dispatch latency from 4 seconds to 2 seconds. The student traces the requirement to a network budget, a timeout in the behavior model, a cloud-versus-onboard allocation, and two stale tests; then produces an impact report showing exact owners and estimated work. That sequence gives more evidence of MBSE competence than twenty disconnected diagrams.

Practice before viewing solutions

  1. What are three technical threads suitable for an oral defense?
  2. Why is a model baseline not a field-operation release?
  3. What should a change-impact demonstration show?

<details> <summary><strong>Show worked answers</strong></summary>

  1. What are three technical threads suitable for an oral defense? Normal operations, credible off-nominal scenario, and a requirement or interface change.
  2. Why is a model baseline not a field-operation release? It does not substitute for implementation, calibrated tests, independent assurance or regulatory/operational permission.
  3. What should a change-impact demonstration show? Exact affected model elements, source decisions, broken assumptions, test implications, owners and controlled status.

</details>

The misconception to avoid

Watch for: A polished model with unresolved interface or evidence gaps should not receive unconditional readiness.

Applied exercise and portfolio handoff

Do: Defend a 15-minute model review and preserve a reproducible, versioned portfolio package. Treat this as preparation for the fuller deliverables and rubric in the original Week 12 guide; the companion is not a substitute for those graded artifacts.
