MBSE value, model purpose, and the document-to-model transition

Companion chapter: EN.645.631, Week 01 · Phase 1 edition 1.0 (2026-10-30)
Original course: Introduction to Model Based Systems Engineering — find Week 1 for assignment, assessment criteria and complete reading plan.
Concepts: model purpose, model authority, source of truth, digital thread
Use of case: Synthetic Autonomous Campus Shuttle case; all values and designs are educational, not field safety guidance.

The question to answer

How can a model reduce uncertainty instead of merely reproducing documents?

Conceptual tutorial

Models are decision instruments

A model is a selective representation of a system, designed for a purpose. A commuter map is useful because it suppresses building details while preserving connected stations. A system model similarly retains requirements, behaviors, interfaces, physical elements and their relations at a degree of precision suited to the decisions it supports. A beautiful diagram that cannot answer a requirements-change question may be less useful than a humble, queryable table.

Distinguish the model (elements with identities, attributes, semantics and relationships), a view (a purpose-specific presentation of a subset of the model), and a document (one possibly exported communication artifact). Two diagrams can show the same model element; editing an image independently does not necessarily update the underlying information. To gain consistency, establish identifiers and ownership. Ask: which representation is authoritative for a requirement, who changes it, and which dependent views must be regenerated?

Choose queries before notation

Begin with decisions: Can we identify all functions lacking an assigned owner? Can we find each requirement whose verification is not planned? Does changing a maximum latency invalidate a network interface design? For each question, name the model data and links needed to answer it. Only then choose the notation or tool. This prevents drawing-based MBSE theater.

A controlled model also has limits. Source observations, test results, assumptions and review judgments often originate outside the modeling tool. A governed link to an external evidence item may be more honest than copying everything into a single repository.

Worked application: follow the reasoning

Shuttle example. A new campus policy changes allowable service hours. In a document-centric workflow, an analyst searches requirements, schedules, interface notes and testing documents manually. In a model-centered workflow, requirement OPS-014 traces to operating scenario SC-02, dispatch function FN-06, timer configuration CFG-03, and tests VT-11 and VT-12. The links do not prove the change is safe; they yield a reviewable impact list that a domain expert can challenge.

Practice before viewing solutions

  1. What distinguishes a model element from a diagram symbol?
  2. Give a useful impact-analysis query for a dispatch change.
  3. When should test evidence remain external to the model?

<details> <summary><strong>Show worked answers</strong></summary>

  1. What distinguishes a model element from a diagram symbol? The element has identity and semantics independent of its views. A diagram symbol is one rendering of it.
  2. Give a useful impact-analysis query for a dispatch change. Find requirements, behaviors, parts, interfaces and verification cases connected to the changed dispatch constraint; also flag absent or suspect links.
  3. When should test evidence remain external to the model? When external configuration, accreditation, raw logs or tool ownership makes a governed URI and metadata preferable to duplicating evidence.

</details>

The misconception to avoid

Watch for: Counting diagrams as evidence of integration confuses output volume with information coherence.
