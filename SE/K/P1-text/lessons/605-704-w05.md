## The question to answer
> How does an abstract use case become a credible collaboration?

## Conceptual tutorial

### Follow the information
A sequence model shows participants and messages in temporal order. Start from a use-case step and ask which object knows the required fact, which one has authority to decide and which one can record a change. Distinguish queries from commands; queries should not silently mutate shared state. A controller may coordinate but should not accumulate every business rule.

Use a responsibility table alongside the sequence: source of request, validation owner, policy owner, reservation authority, event publisher and feedback owner. Every command should have a result or a documented asynchronous acknowledgement. Where messages can arrive late or twice, define idempotency and failure behavior. A happy-path sequence is not enough to establish distributed correctness.

### Check static/dynamic consistency
Every message in a design sequence should be supported by an operation or interface responsibility in the static model. Every newly discovered collaboration may reveal a missing class or association. An interaction view is an *instance scenario*, not universal proof of all allowed state histories. Combine with state models in the next week.

## Worked application: follow the reasoning

**Assignment sequence.** RiderAPI → AssignmentCoordinator (`requestTrip`) → EligibilityPolicy (`check`) → VehicleCatalog (`candidates`) → ReservationService (`reserve`) → EventLog (`append`) → NotificationGateway (`publish`). If reservation times out, retry only with the same idempotency token, then query authoritative state before issuing a second reservation.

## Practice before viewing solutions

1. How does a query differ from a command?
2. Why do retries need idempotency?
3. What indicates a static/dynamic inconsistency?

<details>
<summary><strong>Show worked answers</strong></summary>

1. **How does a query differ from a command?** A query observes; a command requests state change and must express outcome and authorization.
2. **Why do retries need idempotency?** A repeated request might create duplicate reservations or side effects unless requests are recognized or reconciled.
3. **What indicates a static/dynamic inconsistency?** The sequence requires a message not supported by any modeled responsibility or interface.

</details>

## The misconception to avoid

**Watch for:** Large “God controller” lifelines often indicate misplaced domain responsibilities.
