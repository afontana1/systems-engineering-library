## The engineering situation

Short learning intervals fail when evidence is scattered, manually reconciled, or detached from the baseline. The essential question is: **What connected model and data evidence must be available, authoritative, and queryable at each learning decision?**

The central idea of this chapter is **model integration is a versioned evidence problem**. Before a method is selected, the engineer must distinguish the decision being made, what evidence could falsify the leading approach, and which obligations cannot be relaxed. In the Northstar case, engineers, operators, safety leads and suppliers are accountable for different portions of one mission result. A locally successful artifact is not sufficient if the complete outcome is unsupported.

## Explanation: why the method works

A diagram becomes decision-relevant when its elements link to traceable needs, interface versions, tests and released artifacts. A digital thread must support queries such as which tests become stale after a requirement revision. Treat model provenance and change-impact rules as functional capabilities, not as administrative metadata.

A useful way to understand the mechanism is to follow the causal chain explicitly. Start with a stimulus or observed condition; ask which model connects it to the engineering outcome; identify the assumptions that let the model predict anything; and define the next decision. Avoid confusing a convenient dashboard measure with the actual mission variable. Where constraints are hard—such as safety authorization, configuration compatibility or accessibility—treat them as eligibility conditions before computing preferences.

**Deepening the reasoning — Trace query.** Model relationships as typed and versioned edges; a trace to an old requirement revision should be flagged as stale, not merely present. Define change propagation rules and the human role responsible for adjudicating ambiguous traces.

### Connect the theory to the course vocabulary

- Shared knowledge includes short-horizon operational awareness and curated reusable knowledge. Both require ownership and quality controls.
- An authoritative source is designated and governed for a data class; “single source of truth” should not be interpreted as one monolithic tool.
- A digital thread is a governed set of relationships and exchanges that supports questions across lifecycle artifacts.
- The minimum viable thread is selected from decisions and queries. Connecting everything without use cases creates expensive integration with little value.
- Derived views should be reproducible from controlled sources. Manual copies should be identified as latency and inconsistency risks.
- Digital twins will be treated more deeply in EN.645.782; here the concern is whether model/operational evidence shortens learning responsibly.

The statements above originate in the assigned course guide; use them as technical claims to test against a specific scenario, not as terminology to memorize. For each claim, ask what observation could show that it is false or inapplicable in the current design. The same discipline distinguishes an engineering argument from a procedural assertion.

### Digital integration makes engineering knowledge actionable

A shared model or digital thread can reduce delay between discovering a defect and determining its consequences. But digitization does not automatically create shared understanding. If an interface revision is linked to tests without specifying which configuration those tests used, the thread may carry an apparently complete yet invalid assurance claim. Semantic identifiers, revision rules, ownership, and provenance are the prerequisites for useful automation.

Descriptive models show how the system is organized; analytic models predict or constrain performance. Linking them is powerful when the relation is explicit: a configuration change can select a new parameter set, trigger a simulation, and identify evidence needing review. The result is **shorter decision latency**, not mathematical omniscience. Engineers still need to judge whether the model represents the relevant use and whether the data are adequate. A fast incorrect digital workflow merely propagates errors efficiently.

## Graduate depth: the digital thread is a graph of justified meaning

### Traceability is stronger than shared file storage

A digital thread is useful only when the links between engineering artifacts preserve semantics. Copying a requirement identifier into a slide does not establish that a model, test, and release all concern the same requirement revision or configuration. Represent the thread as a typed, directed graph `G = (V, E)`: nodes include needs, functions, logical components, physical configurations, risks, tests, datasets, decisions, and evidence records. Edges have meanings such as *refines*, *allocates*, *verifies*, *derived from*, or *supersedes*. The edge type determines what inference is permissible. “References” and “verifies” are not equivalent relationships.

An engineering baseline is a consistent cut through this evolving graph. Suppose a test result verifies requirement revision R4 on software release S7 and vehicle configuration V2. Reusing that result to claim compliance for R5 or S8 requires an impact argument. A shared folder containing all versions cannot answer that question automatically. Each evidence edge should carry provenance: who produced it, when, with what method, under which assumptions, and with what source artifact hashes or configuration identifiers.

### Semantic consistency and derived information

Model exchange introduces unit, vocabulary, and scope risks. A numerical attribute labeled “availability” might mean dispatch readiness, equipment uptime, or end-to-end mission success. Combining such values in a dashboard creates an apparent common measure without a common operational definition. A semantic contract specifies the entity, property, units, measurement interval, population, permissible null states, and versioned definition. Automated validators can check structure and many unit relationships, but human review remains necessary for ambiguous concepts and stakeholder intent.

For Northstar, suppose a model predicts a 97% chance that a vehicle is dispatch-ready and another estimates a 96% communication link success rate. Multiplying `0.97 × 0.96` would yield about 93.1% only if both probabilities refer to the same mission context and the assumed relevant conditional independence holds. Shared maintenance or power failures may create dependence. An evidence graph should preserve these assumptions instead of allowing a dashboard to silently manufacture a seemingly precise mission availability figure.

### Change impact and assurance across time

A reliable thread supports queries such as: Which claims depend on sensor calibration version C3? Which acceptance results were produced under a retired interface? What is the rationale for allocating a safety function to a particular component? Graph traversal finds candidate impacts, but graph connectivity alone cannot decide substantive equivalence. A changed requirement may be narrower, broader, or semantically different even when its identifier remains stable. Change control must combine machine-assisted dependency analysis with accountable engineering judgment.

The digital thread also connects agile flow to safety and cybersecurity governance. Short development intervals can coexist with robust assurance when evidence links are produced with each increment and stale claims are detectable. Automated checks should fail closed on missing provenance for critical decisions, while lower-consequence exploratory claims may be marked provisional. This prevents two opposite failures: untraceable speed and a digital bureaucracy that records enormous quantities of relationships without improving decision quality.

A well-designed thread does not promise one perfect source of truth for every question. It supports federation among authoritative sources, preserving ownership, access constraints, timestamps, and unresolved contradictions. Its value is measured by the quality and timeliness of decisions it helps reconstruct, not by the number of nodes or clickable links it contains.

## Worked Northstar engineering case

For the accessibility boarding interval, the decision board needs the current need and measure, selected design variant, interface version, participant/trial configuration, simulation version, test results, observed dwell-time distribution, findings, and decision. The thread is implemented with stable identifiers and a query/export, not by copying screenshots into a slide deck. A stale interface record is detected because its version does not match the test configuration.

A change from REQ-14 rev B to rev C affects block BLK-3, service API-2, and tests T-9/T-12. Trace only rev B data and the review falsely concludes evidence is complete.

Work the example in two passes. First compute or trace the nominal outcome, naming the unit of analysis, released configuration and decision threshold. Second change one assumption, such as a degraded interface, heavier demand, invalid provenance or altered stakeholder constraint. If the recommendation changes, identify the threshold at which it changes; if it does not, explain the margin of robustness. A conclusion without its assumptions is not a reusable engineering result.

## A systematic check before accepting the result

1. **Boundary:** What part of the program, process or mission is represented, and what has been excluded?
2. **Evidence:** Which observations, versions, or tests support the premises, and what remains hypothetical?
3. **Causality:** Could the proposed mechanism be confused with a proxy, confounding condition or common dependency?
4. **Decision:** Which alternatives are still feasible, who has authority, and what would force reconsideration?
5. **Assurance:** Which safety, security, accessibility or quality guardrail cannot be traded for speed or convenience?

### Counterexample and failure boundary

A clickable hyperlink does not establish semantic correctness or configuration compatibility.

Evidence query: after REQ-14 B→C, list impacted components, tests, and approvals and justify each invalidated item. Notice that a mathematically consistent answer can still be an inappropriate decision if the intended use or validity assumptions have changed. In professional work, a responsible engineer records that limitation alongside the nominal result.

### Explained response guide

- A strong answer separates the mission outcome from the internal activity metric, states which evidence is authoritative, and specifies an escalation or stop rule when evidence becomes stale.
- For the sensitivity exercise, **Evidence query: after REQ-14 B→C, list impacted components, tests, and approvals and justify each invalidated item.** The correct answer is conditional on the chosen assumption and its justification; there is no single universally preferred architecture or process.
- For the transfer exercise, preserve the causal logic but redefine the boundary, user population, constraints, measurements, and physical limitations. Copying Northstar numbers into another domain would be invalid.

## Step 03 integrated NS-ASE15.1 technical management laboratory: Week 08

### A digital thread is a configuration-specific evidence query

The intended use of a digital thread is not to decorate model elements with links. It is to answer consequential questions: *Which requirement and hazard controls does this particular release satisfy, with which tests, in which environment, and under which approved configuration?* A link's existence is not proof that its endpoints describe the same system version.

In a minimal data model, entities are requirement \(R\), design item \(D\), interface \(I\), test procedure \(T\), execution result \(E\), hazard claim \(H\), configuration \(C\) and authorization \(A\). Edges include \(R\to D\), \(D\to I\), \(I\to T\), \(T\to E\), \(E\to C\), and \(C\to A\). A release query must traverse the graph **and** validate version and evidence state. Missing endpoints or stale execution environments invalidate the query result even if the dashboard shows green labels.

The controlled [item-evidence.csv](../case/item-evidence.csv) is a deliberately narrow demonstration. Its `configuration` column contains `cfg-rNNN` and each row tracks review, integration, assurance, safety and security status. The [Python evidence predicate](../tools/step03_book15_flow.py) rejects a release missing any required Boolean or the matching configuration key. For critical changes the safety result must be explicitly true; for routine changes the field must say `not-applicable`, rather than falsely claiming that a safety test ran.

**Worked counterfactual.** `CHG-007` is safety-classified because seven divides its sequence number. Suppose its review, integration and security results are true for `cfg-r007`, but safety evidence is false: the release gate must refuse it. If a reviewer pastes a pass record from `cfg-r006`, the content may look similar yet the hash/configuration relationship fails. A valid query returns **HOLD**, not an apparently complete percentage score.

**Provenance discipline.** Version the test procedure, simulated environment, dependencies, input data, calibration assumptions, tool version, witness and signed finding disposition. The demonstration script's CSV is reproducible because the JSON source and source code are retained, but that is *only provenance of synthetic computation*. Authenticity, calibrated performance and independent safety judgment require separate evidence. A digital thread can prove what was evaluated without proving that the evaluation was adequate.

**Traceability coverage example.** For 12 mission requirements, suppose nine link to an approved test, eight have results on the current configuration, and seven have independent disposition. Requirement-to-test link coverage is \(9/12=75\%\); configuration-current evidence is \(8/12=66.7\%\); independently accepted evidence is \(7/12=58.3\%\). Reporting only the first metric hides a 16.7 percentage-point evidence-acceptance gap. None of these percentages implies that the seven tests were physically sufficient.

**Explained exercise.** A test passed yesterday, but its lab firmware changed overnight. May its result be reused? Not until the firmware is demonstrated irrelevant to the claim or a re-test/requalification is performed and documented. The digital thread should emit the impact and query failure, not auto-upgrade the result. Connect this lesson to the course's digital-authority model and to Book 9's change-impact analysis.
