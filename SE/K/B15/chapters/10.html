Chapter 10 — Create a cyber-physical DevSecOps and continual-integration system, then red-team a failed increment

Book 15: Agile Systems Engineering · Course EN.645.780 · Week 10
Companion to: Original weekly course guide · Hypothetical laboratory · Book contents

Teaching purpose. The guide defines the assessed engineering deliverable. This chapter builds the underlying mental model and practices reasoning before the lab. All Northstar program details and calculations below are fictional teaching cases, not operational claims.

The engineering situation

Cyber-physical systems cannot continuously manufacture new hardware, but they can continuously integrate models, interfaces, software, firmware, emulators, test assets, evidence, and selected hardware. The essential question is: How should the delivery pipeline expose integration and assurance problems early across mixed disciplines?

The central idea of this chapter is a cyber-physical pipeline has a physical boundary. Before a method is selected, the engineer must distinguish the decision being made, what evidence could falsify the leading approach, and which obligations cannot be relaxed. In the Northstar case, engineers, operators, safety leads and suppliers are accountable for different portions of one mission result. A locally successful artifact is not sufficient if the complete outcome is unsupported.

Explanation: why the method works

Software tests can be fast, but physical actuators, environmental interactions and certification evidence may need simulation, hardware-in-the-loop and controlled field trials. Assign a test environment and authority to every claim. Define what cannot be updated over the air without operational approval.

A useful way to understand the mechanism is to follow the causal chain explicitly. Start with a stimulus or observed condition; ask which model connects it to the engineering outcome; identify the assumptions that let the model predict anything; and define the next decision. Avoid confusing a convenient dashboard measure with the actual mission variable. Where constraints are hard—such as safety authorization, configuration compatibility or accessibility—treat them as eligibility conditions before computing preferences.

Deepening the reasoning — Evidence in CI. Structure the pipeline as model checks→unit tests→integration tests→HIL or environment-qualified tests→review→authorized release. Propagate artifacts and hashes. Where a stage cannot be automated, define a controlled manual gate with clear accountability.

Connect the theory to the course vocabulary

  • Continuous integration means frequently combining and evaluating work against a controlled baseline. It can include models, interface definitions, test assets, and physical surrogates.
  • Pipeline stages should produce evidence and provenance, not only pass/fail status.
  • Higher-fidelity environments are scarce and should be scheduled based on risk and evidence gaps, while lower-cost environments run more frequently.
  • Security includes development environment, dependencies, artifacts, identities, secrets, build integrity, provenance, deployment, and operations.
  • Pipeline metrics should support decisions: lead time, change-failure rate, recovery, defect/evidence age, environment availability, coverage, flakiness, and security finding age.
  • A failed increment is a system learning event. Blameless analysis rejects personal blame but still identifies causal mechanisms, violated controls, and accountable corrective action.

The statements above originate in the assigned course guide; use them as technical claims to test against a specific scenario, not as terminology to memorize. For each claim, ask what observation could show that it is false or inapplicable in the current design. The same discipline distinguishes an engineering argument from a procedural assertion.

The mechanism beneath the method

Cyber-physical continuous integration must coordinate software builds with physical components, models, benches and safety constraints.

Distinguishing related ideas

A rapid digital deployment may outrun the ability to repeat environmental, timing or human-factor checks.

Interpretation and boundary conditions

Use risk-based gates and simulated interfaces without pretending that software-level success substitutes for physical integration evidence.

Graduate depth: cyber-physical continuous integration and assurance

Why a passing pipeline is not a release argument

Continuous integration is often described as automatically building and testing each change. In cyber-physical engineering, an executable result is only one piece of the assurance chain. A configuration may pass unit tests while violating actuator timing, communications safety margins, physical interlocks, or a previously accepted hazard control. The relevant object is a system baseline: software revision, hardware revision, interface definitions, test environment, calibration state, assumptions, and operational permissions. A pipeline result without those identities is difficult to reproduce and may have little relevance to a fielded configuration.

Test evidence is claim-specific. Static analysis can support claims about certain classes of code defects; simulated fault injection can support claims about modeled recovery logic; hardware-in-the-loop tests can support interface and timing claims within the rig's fidelity. None by itself demonstrates safe operation under all real conditions. A strong assurance chain links requirement, hazard, control, implementation, test procedure, observed result, and accepted residual risk. When an upstream interface or model assumption changes, that link makes evidence invalidation visible rather than relying on memory.

Timing, observability, and the simulation-to-physical gap

A control loop can be functionally correct but temporally unsafe. If sensing, computation, communications, and actuation introduce total latency L, the controller operates on information that is at least L old. Jitter matters because the latency is a distribution, not a constant. In a sampled controller, computational deadlines and sample periods interact with plant dynamics: missing a deadline may change the effective feedback law. A test pipeline that only checks output values at nominal sample times cannot establish bounded worst-case behavior.

A software-in-the-loop simulator tests logical behavior with a model of the plant; hardware-in-the-loop introduces real controller hardware and interfaces; physical testing exposes effects that neither simulator includes. Transitioning between these stages creates a fidelity gap. Sensor noise, clock drift, actuator saturation, bus contention, and operator intervention may be absent or idealized earlier. Mismatches are useful findings, not failures to hide. The pipeline should tag results with their evidence level and require higher-fidelity confirmation for claims whose consequences justify it.

Security controls and safety interactions

Cybersecurity can affect operational timing and availability. Authentication, key rotation, intrusion detection, or isolation policies may delay legitimate commands; emergency bypasses may improve immediate responsiveness but create attack paths. Safety and security tradeoffs must be evaluated as coupled system behaviors. Threat modeling should identify attacker capabilities, trust boundaries, and possible cascading effects, while safety analysis considers accidental faults and unsafe control actions. Some mitigations help both; others conflict. Neither team should assume the other's controls are independent.

A useful change-risk strategy computes impact from the dependency structure. A new log-format field might require schema checks and analytics regression, while a change to dispatch authorization may require security tests, human-procedure review, and safety-case reargument. Automated checks can enforce minimum evidence and prevent unauthorized baseline promotion, but final acceptance remains with accountable decision authorities. 'All checks green' means only that the selected checks passed for a specified configuration.

Northstar release example

Suppose Northstar changes priority dispatch to reduce emergency-response latency. The executable tests pass; simulated wait times improve. During HIL execution, clock synchronization drifts under network congestion, causing some requests to be processed out of order. The correct engineering response is to update the timing model, preserve the failed trace, evaluate the safety consequences, and change both tests and architecture if needed. Restarting the pipeline until it passes would destroy the value of evidence.

Continuous assurance is continuous argument maintenance: engineering claims stay connected to their assumptions and evidence as the product evolves. Its success is measured in controlled risk, reproducibility, and earlier defect discovery—not simply in pipeline frequency, automation percentage, or deployment velocity.

Worked Northstar engineering case

A candidate release passes software CI but fails HIL because the emulator used an obsolete interface schema and the build pipeline did not bind test evidence to the interface version. The post-incident analysis identifies missing provenance and promotion criteria, not “tester error.” Corrective actions add schema conformance, signed artifact manifests, environment version checks, and an evidence query before promotion.

A simulated emergency-stop test passes; a delayed sensor update on test hardware violates the stopping response budget. The pipeline must block release on that failure even though the application suite is green.

Work the example in two passes. First compute or trace the nominal outcome, naming the unit of analysis, released configuration and decision threshold. Second change one assumption, such as a degraded interface, heavier demand, invalid provenance or altered stakeholder constraint. If the recommendation changes, identify the threshold at which it changes; if it does not, explain the margin of robustness. A conclusion without its assumptions is not a reusable engineering result.

A systematic check before accepting the result

  1. Boundary: What part of the program, process or mission is represented, and what has been excluded?
  2. Evidence: Which observations, versions, or tests support the premises, and what remains hypothetical?
  3. Causality: Could the proposed mechanism be confused with a proxy, confounding condition or common dependency?
  4. Decision: Which alternatives are still feasible, who has authority, and what would force reconsideration?
  5. Assurance: Which safety, security, accessibility or quality guardrail cannot be traded for speed or convenience?

Counterexample and failure boundary

Do not let a successful emulator run masquerade as operational validation.

Failure drill: fail an HIL timing test, quarantine the build and identify which evidence may still be reused. Notice that a mathematically consistent answer can still be an inappropriate decision if the intended use or validity assumptions have changed. In professional work, a responsible engineer records that limitation alongside the nominal result.

Practise the explanation, not just the procedure

  1. Concept check: Design a pipeline spanning model, software, firmware, interface, simulation, SIL, HIL, physical, security, and evidence stages. Explain: Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
  2. Concept check: Define triggers, environments, configurations, entry/exit criteria, artifact provenance, and failure handling. Explain: Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
  3. Concept check: Apply SSDF and software-supply-chain practices without reducing DevSecOps to scanners. Explain: Give a boundary, an example of evidence, and a concrete case in which the claim would fail.
  4. Sensitivity exercise: Recalculate or re-evaluate the Northstar case after changing one major assumption. State the original and revised decision.
  5. Transfer exercise: Apply evidence in ci to a different engineering system (hospital scheduling, power distribution, or emergency communications). Describe what remains transferable and what does not.

Explained response guide

  • A strong answer separates the mission outcome from the internal activity metric, states which evidence is authoritative, and specifies an escalation or stop rule when evidence becomes stale.
  • For the sensitivity exercise, Failure drill: fail an HIL timing test, quarantine the build and identify which evidence may still be reused. The correct answer is conditional on the chosen assumption and its justification; there is no single universally preferred architecture or process.
  • For the transfer exercise, preserve the causal logic but redefine the boundary, user population, constraints, measurements, and physical limitations. Copying Northstar numbers into another domain would be invalid.

Step 03 integrated NS-ASE15.1 technical management laboratory: Week 10

Cyber-physical DevSecOps with a rehearsed failure and credible recovery

A software build can complete in minutes while its safety claim depends on vehicle hardware, supplier firmware, environmental loading and independent human oversight. A trustworthy cyber-physical pipeline therefore contains different kinds of evidence at different speeds. Fast lint/unit checks cannot impersonate emulator integration; emulator integration cannot impersonate witnessed physical verification.

Proposed pipeline: (1) signed source and requirements baseline; (2) reproducible software build with dependency record; (3) unit, static/security and contract checks; (4) model/emulator regression against stated assumptions; (5) hardware bench and interface tests for applicable changes; (6) hazard/security evidence review; (7) configuration-bound approval by the release authority; (8) staged rollout with instrumentation and an executable rollback plan. Conditional gates must be explicitly documented, not inferred from a generic green status.

The model's gate refuses to release a synthetic change if its review/integration/assurance/security or applicable safety fields are missing, stale, or inconsistent with configuration cfg-rNNN. This is a minimal proof-of-concept for the logical rule; it is not a secure supply-chain verifier, formal OCL specification, production CI tool or independently qualified test suite.

Worked red-team event. An integration test for CHG-014 passed under controller firmware cfg-r014. A new image changes an emergency-stop timeout without updating the test baseline. The green test from the prior image is now stale. Red-team questions are: What changed? Which contracts and hazard claims are affected? Who owns the safety disposition? Which test artifacts are quarantined? Which operator notification and rollback action are required? Until a new controlled test and independent acceptance exist, the release remains HOLD.

Recovery-time decomposition. A detected deployment problem takes 2 hours to diagnose, 3 to produce a compatible rollback image, 4 to re-verify critical interfaces, and 1 for authorization. Under sequential dependence, time to a verified recovery is \(2+3+4+1=10\) hours. Quoting only the 3-hour image-build time as recovery time would ignore the safety evidence and authority. If pre-qualified rollback assets eliminate 2 hours of image preparation but not re-verification, response becomes 8 hours, conditional on equivalence of the rollback configuration.

Metric guardrails. Track change-failure rate and failed-evidence age alongside deployment frequency; mean restore time must start at incident detection and end at a safely authorized restored service. A faster green pipeline with more unverified releases is not an improvement. Dependency pinning, artifact signatures and an SBOM support provenance, while credential management, segregation of duties and audit logging remain operational controls requiring actual implementation.

Exercise with response. An automated simulation passes after the supplier changes a timing parameter, but the model was calibrated to the previous parameter. Is it a release-ready result? No: the simulation's model/parameter applicability is stale, so the pipeline must flag its credibility argument, rerun applicable analyses and perform high-fidelity verification where required. Write the incident record with detection, containment, root-cause hypothesis, corrective action, regression, independent finding closure and authority to resume.
