# Specify interfaces, exchanges, allocations, ownership, and model-based change exposure

## The idea in context

Interfaces should be modeled as contracts: exchanged information or energy, units, valid ranges, timing, initiators, acknowledgment and failure action. Architecture queries can reveal missing ownership, incompatible units, untraced exchanges and unexpected dependencies. Change exposure is a graph property: a revised message schema may affect publishers, subscribers, test data, monitoring and operator procedures. A model query is only useful if relations and identifiers are kept current.

## Worked reasoning: apply it to the shuttle case

A dispatch message contains `eta_s` with a required age below 5 seconds. A consuming display assumes minutes. An interface contract with units and freshness detects the mismatch before integration; a change-impact query identifies all subscribers and tests.

**Assumption to challenge:** Calling a drawn connector an interface specification without semantics or tolerances. Record what observation or test would expose this failure before using the result in a decision.

## Test understanding before reading the answers

The next three questions are adapted from the **original guide's Week 6 knowledge check**, with its answer guidance retained so you can learn and self-check in one place.

1. What is an interface contract?
2. What is an item flow?
3. What is impact overreach?

<details><summary><strong>Reveal guided answers</strong></summary>

1. **What is an interface contract?** The controlled agreement defining the boundary, exchanges, obligations, constraints, quality, failure, compatibility, and verification semantics.

2. **What is an item flow?** A modeled specification of an item or value conveyed across a connector or interaction path.

3. **What is impact overreach?** Treating every graph neighbor as truly affected without engineering confirmation.

</details>
