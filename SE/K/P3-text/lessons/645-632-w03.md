# Develop and analyze the functional architecture from black-box behavior to allocated white-box functions

## The idea in context

Functional decomposition is about responsibility and flow, not organizational departments. Start from black-box inputs, outputs, controls and required transformations. Decompose only far enough to make allocations, interface exchanges and testable conditions explicit. Every child function must contribute to its parent; orphan functions or unbalanced inputs reveal model defects. Activity, sequence and functional-flow views are complementary and should agree about triggers, outputs and exceptions.

## Worked reasoning: apply it to the shuttle case

A black-box function “transport passenger” can be refined into authenticate request → assign resource → board → move → alight → close trip. If a boarding event produces no custody record for mobility assistance, the flow contains an omitted interface; adding a diagram label alone does not close the gap.

**Assumption to challenge:** Treating every box on a functional diagram as an existing hardware component. Record what observation or test would expose this failure before using the result in a decision.

## Test understanding before reading the answers

The next three questions are adapted from the **original guide's Week 3 knowledge check**, with its answer guidance retained so you can learn and self-check in one place.

1. What is black-box behavior?
2. What is white-box behavior?
3. Why model enabling functions?

<details><summary><strong>Reveal guided answers</strong></summary>

1. **What is black-box behavior?** Externally observable transformation and interaction without exposing internal performers.

2. **What is white-box behavior?** Behavior expressed through internal responsibilities, interactions, and allocations.

3. **Why model enabling functions?** They make mission behavior possible, safe, secure, supportable, recoverable, and maintainable.

</details>
