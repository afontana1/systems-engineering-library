## The idea in context

In a discrete-event simulator, state changes only at scheduled events: arrivals, service start, completion, breakdown or reneging. A priority queue holds events ordered by time and tie-break rule; resource logic prevents impossible double allocation. Track time-weighted queue length separately from passenger-averaged waiting. Warm-up and finite horizon choices depend on the modeled system.

## Worked reasoning: apply it to the shuttle case

Two vehicles each serve one rider group every 10 min. If arrivals average 15 groups/hour, nominal maximum capacity is 12/hour. A persistent queue is expected; the simulator should not show stable zero backlog.

**Assumption to challenge:** Allowing a resource to be seized twice or dividing a time-weighted queue sum by the wrong denominator. Record what observation or test would expose this failure before using the result in a decision.

## Test understanding before reading the answers

The next three questions are adapted from the **original guide's Week 5 knowledge check**, with its answer guidance retained so you can learn and self-check in one place.

1. What advances time in a discrete-event simulation?
2. Why use deterministic cases?
3. What is an invariant?

<details><summary><strong>Reveal guided answers</strong></summary>

1. **What advances time in a discrete-event simulation?** The simulation clock jumps to the next scheduled event time.

2. **Why use deterministic cases?** They create predictable results for logic verification independent of stochastic noise.

3. **What is an invariant?** A property that must remain true throughout execution, such as nonnegative queue length or capacity limits.

</details>
