# Timing, interfaces, allocations, and Functional Architecture Review

**Companion chapter:** EN.645.767 · Week 06 · Phase 2 edition 1.0 (2026-10-30)

**Concepts:** end-to-end timing, interface ownership, functional allocation, Functional Architecture Review  
**Case:** Fictional Autonomous Campus Shuttle, dispatch and transport service; all figures are illustrative, not deployment guidance.

## The engineering question

> How can an architecture review expose missing contracts before hardware is chosen?

## Conceptual tutorial

### Follow budgets across organizational seams
An end-to-end response is a sum or composition of contributions: queueing, computation, communication, actuation, and operator delay. Under a serial simplification, total latency is the sum of stage latencies; under parallel activity it is governed by a critical-path maximum. Worst-case and percentile budgets cannot be added indiscriminately without assumptions about correlation and distribution.

An interface needs a sender, receiver, exchanged item, schema/units, update rate, accuracy, security boundary, state/timeout behavior, failure response and accountable owner. The Functional Architecture Review (FAR) should ask whether every mission-critical function and exchange is represented, whether performance budgets are plausible, and whether a proposed performer can be substituted without invalidating requirements.

### Make review findings actionable
A review exit is not an attractive diagram. Use a discrepancy log: issue ID, evidence, consequence, accountable owner, resolution test and closure authority. Create distinct outcomes: approve for concept development, approve with tracked risks, or rework a missing functional argument. Explicitly retain unresolved assumptions instead of converting them to "TBD" in supposedly controlled interfaces.

## Worked example: follow the reasoning

**Budget.** An illustrative notification path allocates 80 ms ingress, 150 ms queue, 120 ms decision, 100 ms storage, and 200 ms network: serial sum 650 ms. A 900 ms target leaves 250 ms nominal margin. This does not prove the 99th percentile, and a loss of network connectivity is an entirely different mode requiring alternate behavior. Record allocation, condition, evidence method and owner for each stage.

## Retrieval questions — attempt these first

1. Why is a 250 ms nominal timing margin not a tail-latency guarantee?
2. Name four attributes an interface contract must define.
3. What closes an architecture-review action?

<details><summary><strong>Reveal explained answers</strong></summary>

1. **Why is a 250 ms nominal timing margin not a tail-latency guarantee?** Variability, correlations, load and failure modes can move observed latency far beyond nominal values.
2. **Name four attributes an interface contract must define.** At minimum: roles, exchanged content and units, timing, error policy; include ownership and version.
3. **What closes an architecture-review action?** Evidence-backed resolution accepted by the authorized reviewer, not a promise or status label alone.

</details>

## Critical misconception

**Watch for:** Adding stage p99 figures as if they describe a coherent system p99 can produce invalid conclusions.
