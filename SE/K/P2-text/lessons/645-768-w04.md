**Concepts:** physical architecture, interface control document, technical budgets, margins  
**Case:** Fictional Autonomous Campus Shuttle, dispatch and transport service; all figures are illustrative, not deployment guidance.

## The engineering question

> When is a physical design coherent enough for independent disciplines to build against it?

## Conceptual tutorial

### Real components bring real constraints
Move from logical functions to candidate hardware, software, humans, facilities and external services. Each element requires a defined location, environment, power/data/mechanical boundaries, responsibility and configuration. Interface Control Documents (ICDs) need units, connector/protocol definition, message structure, timing, safety/security assumptions, version and change authority. An arrow between two boxes is not an ICD.

Track technical budgets for mass, energy, power, thermal load, network capacity, timing and availability where applicable. A budget needs nominal estimates, uncertainty, current margin and a closure plan. Margin is not a magic percentage: different domains handle uncertainty and contingency differently. Keep "estimated" separate from "measured" and record dependencies between assumptions; one larger battery may increase both energy capacity and vehicle mass.

### Evaluate architecture choices at system level
Alternative allocation patterns can move risk: centralized processing simplifies some policies but increases connectivity dependence; edge processing can preserve degraded operation while complicating synchronization. Assess change isolation, cyber boundary, failure containment and maintainability in addition to nominal functionality.

## Worked example: follow the reasoning

**Interface and budget example.** A gateway can publish telemetry at 2 Hz. With 250 bytes per message and 20 vehicles, raw payload rate is `2 × 250 × 20 = 10,000 bytes/s` before transport framing, encryption, retries and spikes. An ICD must specify data encoding and allowed staleness. Treat 10 kB/s as only the payload baseline; use a separate network model to account for overhead and bursts.

## Retrieval questions — attempt these first

1. Why is a connection line insufficient for implementation?
2. What does a technical-margin register need beyond the numerical margin?
3. Why is 10,000 bytes/s not a complete bandwidth estimate?

<details><summary><strong>Reveal explained answers</strong></summary>

1. **Why is a connection line insufficient for implementation?** It omits syntax, semantics, ownership, version, timing, fault response and physical constraints.
2. **What does a technical-margin register need beyond the numerical margin?** Source and uncertainty, measurement method, trend, authority, and a response if margin erodes.
3. **Why is 10,000 bytes/s not a complete bandwidth estimate?** Headers, retransmissions, encryption, burst conditions and additional message types are excluded.

</details>

## Critical misconception

**Watch for:** Using a single average to size peak capacity confuses nominal operation with required operating envelope.
