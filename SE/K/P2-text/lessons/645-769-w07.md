## The engineering question

> When can automated and cyber test results be trusted as engineering evidence?

## Conceptual tutorial

### The tools are part of the evidence system
Automation reduces manual variability but can automate wrong assumptions. Validate the harness: clock discipline, stimulus correctness, parser logic, result calculation, configuration capture and independent spot checks. The test toolchain needs versioning and access control. A result marked "pass" with no raw data or script hash cannot be independently reproduced.

Security test objectives should connect to threat and trust-boundary analyses. Authentication, authorization, replay resistance, data integrity, audit fidelity and recovery behavior require testable claims. Penetration testing can reveal vulnerabilities in a defined scope, but a clean scan cannot establish the absence of vulnerabilities. Include patch level, configuration, ruleset and authorization of intrusive tests.

### Protect evidence integrity
Store raw logs immutably where appropriate, preserve checksums, document transformations, and restrict access to sensitive data. Make derived charts reproducible from source data and an analysis script. If a test executor manually changes a file after collection, the audit trail should show it.

## Worked example: follow the reasoning

**Automation defect.** A harness measures response time only for records with both timestamps, silently dropping network timeouts. Its computed p99 appears acceptable, but the acceptance population is wrong. Add a completeness check comparing sent and received IDs, classify missing responses, and test the analysis script against a fixture containing known timeouts.

## Retrieval questions — attempt these first

1. Why must a test harness itself be validated?
2. Does a clean vulnerability scan prove security?
3. How can a checksum improve evidence trust?

<details><summary><strong>Reveal explained answers</strong></summary>

1. **Why must a test harness itself be validated?** Harness bugs or omissions can manufacture false pass results despite correct device behavior.
2. **Does a clean vulnerability scan prove security?** No. It only supports limited claims within scanner, scope, configuration and technique.
3. **How can a checksum improve evidence trust?** It helps establish that stored evidence bytes have not changed since a known point, alongside provenance controls.

</details>

## Critical misconception

**Watch for:** Data completeness is part of the measurement contract, not an optional cleaning step.
