# Allocate requirements and define component functions

**Companion chapter:** EN.645.768 · Week 03 · Phase 2 edition 1.0 (2026-10-30)  
**Original study guide:** [System Design & Integration](../../../C/P2/EN645768.md) — consult **Week 3** for the complete assignment, original source readings and mastery rubric.  
**Concepts:** requirements allocation, functional decomposition, component responsibility, allocation rationale  
**Case:** Fictional Autonomous Campus Shuttle, dispatch and transport service; all figures are illustrative, not deployment guidance.

## The engineering question

> How does a requirement become one or more accountable component obligations?

## Conceptual tutorial

### Allocation is engineering, not column-filling
At the system level, a requirement is often satisfied through multiple elements. A response-time requirement, for example, may be allocated across gateway, network, scheduler and persistence service. Mechanical, electrical, human and software subsystems also exchange constraints. Build an allocation matrix that states who performs each function, who supplies enabling interfaces, who verifies the lower-level property and how the combination satisfies the parent requirement.

A good derived requirement follows from a transparent budget or analysis. If one stage receives a 150 ms allowance, show why this share is feasible and which test can measure it. Distinguish responsibility allocation from verification delegation: testing components individually does not always demonstrate system-level compliance because interactions can add unexpected delays and failure modes.

### Inspect boundary failure modes
Search for requirements allocated to no component, duplicate ownership, missing external-system actors, and obligations that fall between providers. For every interface, ask who is responsible when a message is missing, late, duplicated or malformed. Trace a mission scenario end-to-end and follow both the normal and failure path.

## Worked example: follow the reasoning

**Latency allocation.** Parent requirement `R-14` targets 900 ms. Assign budget shares of gateway 80 ms, queue 150 ms, scheduler 120 ms, database 100 ms and notification network 200 ms; reserve 250 ms. Each component owner receives a measurable budget in a defined nominal workload. System integration must still measure full-path latency and characterize variability.

## Retrieval questions — attempt these first

1. Why can every component pass its own test while a system fails?
2. What does a duplicate allocation need to specify?
3. What should a derived lower-level budget trace to?

<details><summary><strong>Reveal explained answers</strong></summary>

1. **Why can every component pass its own test while a system fails?** Interactions, load, propagation, cross-component timing and shared resource contention can violate end-to-end constraints.
2. **What does a duplicate allocation need to specify?** Primary accountable owner, contributors and exact shared boundary, avoiding unowned or conflicting authority.
3. **What should a derived lower-level budget trace to?** A parent requirement, analysis assumptions, interface reference and planned evidence.

</details>

## Critical misconception

**Watch for:** Splitting a timing target into numbers that sum correctly is not proof the underlying components can achieve those numbers.
