Construct the integration test approach, SIL/HIL paths, and informal tests

Concepts: integration test plan, SIL, HIL, fault injection, informal test
Case: Fictional Autonomous Campus Shuttle, dispatch and transport service; all figures are illustrative, not deployment guidance.

The engineering question

How should informal integration tests progress toward representative system evidence?

Conceptual tutorial

Test interactions deliberately

Integration tests should detect mismatched assumptions between elements: data types, units, state transitions, timeouts, startup/shutdown order, resource contention, authentication and error recovery. Arrange staged testing from stubs and service emulation to system-in-the-loop and, where justified and safe, hardware-in-the-loop. Each environment needs a stated fidelity claim and versioned configuration.

Informal tests are valuable for discovering problems before formal verification; they are not necessarily accepted qualification evidence. Write repeatable exploratory scripts and retain logs, then promote stable procedures through review for later formal use. Distinguish test coverage of normal workflows from coverage of boundary conditions and faults. Duplicate, delayed, malformed and reordered messages can expose state-management defects missed by happy-path tests.

Keep integration safe and diagnosable

Use isolation boundaries, rollback points and explicit stop conditions, particularly where hardware can move or cause harm. A simulated trip workflow cannot authorize autonomous vehicle deployment. Identify which evidence is exclusively about dispatch IT and which would require independently approved physical-system test programs.

Worked example: follow the reasoning

Fault-injection sequence. Configure a simulated gateway and dispatch build D-21. Inject a vehicle_available message twice, then delay a subsequent unavailable message. Verify the assignment service checks sequence/version and does not create two active assignments. Record expected behavior, actual event log, timestamp reference, configuration and defect disposition.

Retrieval questions — attempt these first

  1. What is the difference between SIL and HIL?
  2. Why do informal tests matter before formal qualification?
  3. Why must duplicate messages be tested explicitly?

<details><summary><strong>Reveal explained answers</strong></summary>

  1. What is the difference between SIL and HIL? SIL commonly exercises software with simulated surroundings; HIL includes relevant physical hardware in a controlled test loop.
  2. Why do informal tests matter before formal qualification? They cheaply expose architecture, interface and test-procedure defects before evidence gates.
  3. Why must duplicate messages be tested explicitly? Real transport can retry or replay, and non-idempotent handlers can corrupt state.

</details>

Critical misconception

Watch for: Calling every integration test a qualification test erases the meaning of approval and procedure control.
